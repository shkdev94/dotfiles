# 목록·이미지·스크롤 점검

긴 목록, 셀 재사용 문제, 스크롤 끊김이나 이미지 메모리를 다룰 때 읽는다. 목록 컴포넌트 교체 전에 현재 병목과 데이터 규모를 확인한다.

## 목록 선택과 셀 수명

- 기존 `FlatList`·`SectionList` 또는 프로젝트의 목록 라이브러리를 우선 활용한다. FlashList 같은 대안은 측정된 문제, 기능 차이와 설치 버전의 아키텍처 요구를 비교해 선택한다.
- 같은 방향의 `ScrollView` 안에 긴 가상화 목록을 넣어 가상화가 무력화되는지 확인한다. 가능하면 목록의 header·footer·section으로 한 스크롤 소유자 안에 구성한다.
- key는 데이터의 안정적인 ID를 사용한다. 삽입·정렬되는 목록에 인덱스를 항목의 정체성으로 쓰지 않는다.
- 셀 재활용을 지원하는 목록에서는 로컬 state·비동기 이미지·애니메이션 값이 새로운 항목에 맞게 갱신되는지 확인한다. 라이브러리가 제공하는 재활용 API와 수명을 따른다.
- 여러 셀 종류를 재활용한다면 `getItemType` 같은 설치 버전의 API로 구분할 수 있는지 확인한다. 타입 분류는 실제 구조 차이를 반영하며 항목마다 고유한 타입을 만들지 않는다.

## 렌더링과 배치

- 부모의 불필요한 갱신과 넓은 전역 상태 구독을 먼저 좁힌다. 행 내부의 비싼 파싱·정렬·포맷 준비는 입력이 바뀔 때만 실행하도록 정리한다.
- `memo`나 안정적인 callback은 행의 실제 렌더 비용 또는 목록의 참조 계약에 맞춰 사용한다. 인라인 객체·함수라는 이유만으로 모두 별도 변수와 Hook으로 옮기지 않는다.
- `FlatList`의 `getItemLayout`은 높이와 간격을 정확히 계산할 수 있을 때 사용한다. 가변 높이에 잘못된 계산을 넣으면 스크롤 위치와 보이는 항목이 틀어질 수 있다.
- 초기 렌더 수, window·batch 크기는 빈 영역·반응성·메모리의 균형을 확인하며 조정한다. 기기와 항목 복잡도에 무관한 고정 권장값을 적용하지 않는다.
- 화면 밖 항목이나 삭제된 항목에 대한 비동기 작업·구독이 남지 않는지 확인한다. 페이지 요청은 중복 트리거, 실패 후 재시도와 끝 상태를 처리한다.

## 이미지와 측정

- 표시 크기에 맞는 이미지 소스와 크기·종횡비를 제공해 과도한 디코딩과 레이아웃 이동을 줄인다. 로딩 실패·캐시·재활용 중 이전 이미지 표시를 확인한다.
- 기존 이미지 컴포넌트가 필요한 캐시·전환 기능을 제공하는지 확인한다. `expo-image`를 포함한 새 라이브러리 도입은 기능과 네이티브 빌드 비용을 비교한다.
- 스크롤 위치 전체를 state로 올리는 대신 애니메이션 값이나 화면 노출·임계값 이벤트 등 필요한 결과만 구독한다. 분석 이벤트는 화면 갱신과 분리하고 불필요한 중복을 줄인다.
- 같은 데이터·기기·빌드 모드에서 빠른 스크롤, 다시 돌아오기, 삽입·삭제, 페이지 추가를 비교한다. 프레임·메모리 측정과 함께 잘못 재사용된 입력·선택 상태가 없는지도 확인한다.
