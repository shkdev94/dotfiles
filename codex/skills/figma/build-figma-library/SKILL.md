# Figma 디자인 시스템 구축

## 목표와 역할

코드와 Figma의 실제 토큰·컴포넌트 계약을 맞추고, 재사용 가능한 변수를 바인딩한 컴포넌트를 만든다. 결과에는 만든 자산의 ID, 대응 관계와 구조·화면 검증 결과를 포함한다.

## 조사와 범위

[use-figma](../use-figma/SKILL.md)를 함께 적용한다. 코드의 토큰·테마·컴포넌트와 Figma의 변수·스타일·인스턴스를 읽고 차이를 정리한다. `get_libraries` 다음 `search_design_system`으로 재사용할 자산을 확인한다. 자세한 검색 방식은 [디자인 시스템 재사용](../build-figma-design/references/design-system.md)을 따른다.

코드와 Figma가 충돌하면 근거를 나란히 제시하고 어느 쪽을 기준으로 할지 결정한다. 기존 지시로 판단할 수 없는 충돌만 질문한다. 토큰과 컴포넌트 범위를 정하고 이미 있는 기반은 재사용한다.

## 구축 순서

1. **변수와 스타일:** 필요한 컬렉션·모드를 정하고 primitive, 이를 참조하는 semantic variable, 텍스트·효과 스타일을 만든다. 모든 변수가 필요한 scope와 실제 코드 이름에 대응하는 code syntax를 갖도록 한다.
2. **파일 구성:** 기존 페이지·이름 규칙에 맞춰 작업 위치를 정한다. 전체 시스템 구축일 때는 토큰과 사용법을 읽을 수 있는 문서를 포함한다. 작은 보완에 새 표지·문서 페이지를 일률적으로 추가하지 않는다.
3. **컴포넌트:** 의존하는 기본 컴포넌트부터 만든다. auto-layout과 변수 바인딩을 적용하고 필요한 variant·TEXT·BOOLEAN·INSTANCE_SWAP 속성을 실제 자식 노드에 연결한다.
4. **통합:** variant 수, 바인딩, 이름과 접근성 상태를 확인한다. 요청 범위의 Code Connect 연결을 완성하고 구성한 화면을 검증한다.

변수·variant 작성 시 [토큰과 컴포넌트 규칙](references/tokens-and-components.md)을 읽는다. 같은 상태를 바꾸거나 이전 결과에 의존하는 쓰기는 순서대로 수행한다.

## 상태와 복구

- 긴 작업은 생성한 페이지·노드·변수·스타일의 정확한 ID와 단계별 완료 상태를 로컬 작업 기록에 남긴다. Figma 객체에 내부 작업 상태를 억지로 저장하지 않는다.
- 재개하거나 오류를 복구할 때 기록과 실제 파일을 다시 대조한다. 이름만으로 사용자 노드를 삭제하지 않는다.
- 호출이 반환한 ID·개수·경계가 충분하면 같은 구조 검사를 반복하지 않는다. 검증된 기반 위에 다음 작업을 구성한다.
- 한 컴포넌트의 생성이 실패했다면 부분 적용을 먼저 확인해 해당 부분만 복구한다. 전체 파일을 초기화하지 않는다.
