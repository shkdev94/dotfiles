# 좋은 React 코드 작성

## 목표와 역할

요구한 UI 동작을 구현하면서 컴포넌트의 공개 API, 상태 변경과 데이터 흐름을 이해하기 쉽게 유지한다. React의 렌더링 모델과 프로젝트의 실행 환경에 맞게 구조와 성능을 판단한다.

- 입력은 요구사항, 관련 컴포넌트·훅·호출자, 데이터 요청 경로와 현재 실행 환경이다.
- 결과물은 요청 범위의 코드 변경, 관련 검증 결과와 중요한 선택 근거다. 성능 개선을 보고할 때는 측정 결과와 구조상 기대 효과를 구분한다.
- [write-good-code](../write-good-code/SKILL.md)의 공통 구현 기준을 따른다. TypeScript를 쓰면 [write-good-typescript](../write-good-typescript/SKILL.md)를 함께 적용한다.
- 특정 상태 라이브러리, 프레임워크 버전이나 패턴으로 전면 전환하지 않는다. 코드 리뷰 요청이면 수정 여부는 해당 요청 범위를 따른다.

## 먼저 확인할 환경

- 실제 React 버전, React Compiler 사용 여부, 빌드 도구와 기존 데이터·상태 관리 방식을 확인한다. Next.js이면 버전과 라우터, Server Component 사용 여부도 확인한다.
- 현재 동작과 관련된 호출자, 로딩·오류·빈 상태, 입력과 제출 흐름을 읽는다. 사용자가 요청한 변화와 보존할 동작을 구분한다.
- 버전별 API와 캐시 기본값을 기억만으로 가정하지 않는다. 변경에 필요한 공식 문서를 확인하고 기존에 동작하는 API를 최신 예제라는 이유로 일괄 교체하지 않는다.

## 컴포넌트와 상태

- 서로 배타적인 모드를 여러 boolean prop으로 조합해 잘못된 상태를 허용하는지 확인한다. 목적이 다른 변형은 명시적인 컴포넌트·구별된 타입·합성 중 단순한 방식으로 표현한다. `disabled`, `open` 같은 독립적인 boolean 자체를 금지하지 않는다.
- 화면 구성이나 공유 상태의 경계를 바꿀 때는 [컴포넌트 합성과 상태 계약](references/composition.md)을 읽는다. 단순한 props 전달로 충분한 곳에 provider나 compound component를 추가하지 않는다.
- 상태는 필요한 소비자의 가까운 공통 소유자에 둔다. props와 state에서 계산되는 값은 렌더링에서 도출하고, 같은 값을 별도 state와 Effect로 동기화하지 않는다.
- 사용자 동작 때문에 실행하는 작업은 이벤트 핸들러에서 처리한다. Effect는 외부 시스템과의 동기화에 사용하고 구독·타이머·요청의 수명과 정리를 확인한다. 의존성 경고를 숨기려고 값을 ref로 옮기거나 의존성을 누락하지 않는다.
- 이전 상태에 의존하는 갱신은 함수형 갱신을 사용한다. 화면 갱신이 필요한 데이터는 state에, 렌더링에 쓰이지 않는 핸들·일시적 값은 ref에 둔다.
- Hook 호출 규칙과 렌더링의 순수성을 지킨다. 목록의 key는 항목의 정체성을 유지해야 하며, 입력·포커스·선택 상태가 잘못 재사용되거나 초기화되지 않는지 확인한다.

## 데이터와 성능

- 먼저 불필요한 요청 직렬화, 중복 요청, 큰 클라이언트 번들과 과도한 데이터 전달을 확인한다. 미세한 계산 최적화부터 일괄 적용하지 않는다.
- 데이터 요청, Next.js 경계 또는 성능을 바꿀 때는 [요청·번들·렌더링 성능](references/performance.md)을 읽는다. 서버용 지침을 일반 클라이언트 React 앱에 적용하지 않는다.
- 필요한 상태만 구독하고 고빈도 변경의 영향 범위를 좁힌다. `memo`, `useMemo`, `useCallback`은 확인된 재계산·렌더링 비용이나 참조 안정성 요구에 맞게 적용한다. Compiler가 활성화된 코드에 수동 메모이제이션을 기계적으로 추가하지 않는다.
- 접근성 의미와 키보드·포커스 동작을 보존한다. SSR에서는 서버와 클라이언트의 초기 출력을 맞추고 hydration 경고를 숨기는 방식으로 불일치를 해결하지 않는다.

## 검증과 결과

- 저장소의 관련 타입 검사·린트·테스트·빌드를 수행한다. Effect·구독 변경은 정리와 재실행, 비동기 변경은 늦은 응답·중복 제출·오류 표시를 확인한다.
- 컴포넌트 합성 변경은 실제 호출자와 각 변형의 공개 동작을 확인한다. 필요한 UI 테스트는 [write-ui-unit-test](../../testing/write-ui-unit-test/SKILL.md)의 기준을 적용한다.
- 성능 작업은 같은 시나리오에서 요청 순서, 번들 분석, React Profiler나 브라우저 측정 중 문제에 맞는 근거를 비교한다. 측정하지 않은 개선 수치를 만들지 않는다.
- 결과에 달라진 동작, 구조 선택의 이유, 실제 검증과 미확인 범위를 보고한다. 요청 없이 커밋·PR 게시까지 이어가지 않는다.

참고: Vercel의 [Composition Patterns](https://github.com/vercel-labs/agent-skills/tree/main/skills/composition-patterns)와 [React Best Practices](https://github.com/vercel-labs/agent-skills/tree/main/skills/react-best-practices). 두 스킬의 구성·성능 판단을 통합하고, 버전과 적용 조건에 따라 필요한 지침만 남겼다.
