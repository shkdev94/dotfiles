# UI 유닛 테스트 작성

## 목표와 역할

사용자가 화면에서 보고 수행하는 핵심 동작을 테스트로 보호한다. UI 컴포넌트와 관련 훅의 회귀를 발견하면서 내부 구현을 바꾸는 리팩터링을 방해하지 않는 테스트를 작성하는 것이 이 스킬의 역할이다.

- 입력은 대상 UI·훅, 기대 동작, 관련 이슈나 검토 결과, 기존 테스트다. 이슈가 없어도 요청된 동작과 코드의 계약이 명확하면 진행한다.
- 실패 영향과 기존 검증 범위를 기준으로 시나리오를 선별하고, 사용자 상호작용과 관찰 가능한 결과를 AAA 방식으로 작성·실행한다.
- 결과물은 UI 테스트 코드, 필요한 최소 테스트 설정·픽스처, 실제 실행 결과와 확인하지 못한 범위다.
- 모든 컴포넌트의 테스트나 커버리지 수치 달성을 목표로 하지 않는다. 순수 비즈니스 규칙, E2E, 시각 검증은 별도 범위로 구분한다. 요청 없이 제품 수정이나 PR 생성으로 확대하지 않는다.
- 설명과 테스트 이름은 한국어로 쓰고, 이름은 `유효하지 않은 이메일 제출 시 오류 메시지를 표시한다`처럼 조건·행동·결과를 드러낸다.

## 대상 선정

- 저장소의 적용 지침, 테스트 도구와 버전, 기존 테스트·픽스처·설정·실행 명령을 먼저 확인한다. 연결된 이슈나 검토 결과가 있으면 기대 동작과 완료 기준의 근거로 읽는다.
- 기존 테스트가 무엇을 보장하는지 확인하고 중복을 피한다. 모든 컴포넌트와 훅에 테스트를 만들지 않는다.
- 조건부 렌더링, 권한별 UI, 로딩·오류·빈 상태, 폼 검증과 제출, 사용자 상호작용, 보고된 UI 회귀를 우선한다.
- 단순 전달 함수, 상수, 프레임워크 자체 동작, 로직 없이 props를 표시하는 컴포넌트는 별도 테스트의 가치가 있는지 판단한다. 타입 검사나 기존 상위 테스트가 이미 보장하는 내용을 반복하지 않는다.
- 커버리지 숫자만을 위한 테스트는 추가하지 않는다. 저장소의 커버리지 기준이 있으면 따르되 의미 없는 assertion이나 제외 설정으로 맞추지 않는다.
- 사용자가 정한 작업 범위 안에서 대상과 핵심 시나리오를 간단히 정리하고 작성한다. 기대 동작이 불명확하고 결과를 바꿀 수 있을 때만 확인한다.

## UI 테스트 범위

- 작성 전에 [UI 테스트 지침](references/ui-tests.md)을 읽는다. React에서는 RTL·userEvent·MSW 지침을 적용하고, 다른 UI 프레임워크에서는 사용자 관점 원칙을 기존 도구에 맞게 적용한다.
- 사용자 입력, 화면 상태, 접근 가능한 이름과 역할, 폼 제출과 오류 표시를 검증한다. React 생명주기와 연결된 커스텀 훅의 공개 동작도 포함한다.
- 훅에서 호출하는 순수 계산·도메인 규칙 자체는 비즈니스 로직 유닛 테스트의 범위다. UI 테스트에서는 화면과의 연결을 검증하고 동일한 입력 조합을 중복 나열하지 않는다.
- 컴포넌트 테스트로 실제 브라우저 레이아웃·화면 간 흐름·실제 서비스 통합을 모두 검증했다고 주장하지 않는다. 별도 E2E나 시각 검증이 필요한 범위는 보고하며 요청 없이 새로운 테스트 체계를 도입하지 않는다.

## AAA와 가독성

- 각 테스트를 Arrange(입력·환경 준비), Act(검증할 행동), Assert(관찰 결과 검증) 순서로 구성한다. 빈 줄로 구간을 구분하고, 복잡할 때만 구간 주석을 추가한다.
- 테스트 하나는 하나의 동작 시나리오를 검증한다. 폼 입력과 제출처럼 한 시나리오를 이루는 여러 상호작용은 허용한다. 무관한 행동과 검증을 이어 붙이지 않는다.
- 하나의 결과를 설명하는 관련 assertion은 여러 개 사용할 수 있다. assertion 수를 줄이려고 중요한 검증을 빼지 않는다.
- 준비 데이터는 테스트 의도가 드러나는 최소값을 사용한다. 반복 설정은 기존 헬퍼를 재사용하고, 추상화가 입력과 기대 결과를 숨기지 않게 한다.
- 기대값은 요구사항과 계약에서 도출한다. 테스트 안에서 구현 알고리즘을 다시 계산하거나 실제 반환값을 그대로 기대값으로 만들지 않는다.
- 내부 변수·비공개 메서드·호출 순서보다 공개된 입력·출력과 관찰 가능한 부수효과를 검증한다. 호출 자체가 계약인 경우에만 경계에서 호출 인자를 검증한다.

## 격리와 모킹

- 테스트 간 실행 순서나 공유 가변 상태에 의존하지 않는다. 캐시·스토어·픽스처를 격리하고 등록한 핸들러·spy·타이머·구독을 정리한다.
- 실제 네트워크, 현재 시각, 무작위 값 때문에 결과가 달라지지 않게 필요한 경계만 제어한다. 구현과 무관한 의존성까지 전부 모킹하지 않는다.
- 시간 자체가 계약인 경우 fake timer를 사용하고 원래 타이머로 복원한다. 고정 sleep이나 재시도로 불안정성을 숨기지 않는다.
- 기존 러너와 라이브러리를 우선 사용한다. 도구가 없으면 필요한 최소 설정만 작업 범위와 저장소 정책에 맞게 도입하며 무관한 마이그레이션은 하지 않는다.

## 실행과 결과

- 작성·수정한 테스트를 먼저 실행하고 관련 테스트 및 저장소가 요구하는 검증을 수행한다. 새 실패나 미해결 위험이 없으면 불필요하게 전체 테스트를 반복하지 않는다.
- 회귀 테스트는 가능한 경우 기존 결함에서 실패하고 수정 후 성공하는지 확인한다. 확인을 위해 사용자 변경을 되돌리거나 실제 환경을 변경하지 않는다. 확인하지 못한 경우 한계를 명시한다.
- 실패하면 잘못된 테스트·환경 문제·실제 제품 결함을 구분한다. 통과시키기 위해 기대값을 약화하거나 테스트를 skip하지 않는다. 제품 수정이 요청 범위에 없으면 발견한 결함을 보고한다.
- 결과에는 추가한 시나리오와 선정 이유, 실행 명령과 결과, 실행하지 못한 검증을 간단히 적는다. 선택하지 않은 모든 파일을 나열할 필요는 없다.
- 요청 없이 커밋·PR 생성·이슈 등록까지 이어가지 않는다.
