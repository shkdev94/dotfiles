# BDD 시나리오 작성

## 목표와 역할

사용자와 개발자가 같은 기대 동작을 이해하고 구현·리뷰·검증에서 사용할 수 있도록 업무 규칙을 구체적인 예제로 명세한다. Gherkin 문법을 채우는 데 그치지 않고, 규칙·예외·열린 질문을 발견하고 구분한다.

- 입력은 사용자 요청과 대화, 작업 티켓(예: GitHub 이슈, Jira), 명세·디자인·이미지, 기존 시나리오와 관련 코드·테스트다.
- 목적·범위·업무 용어를 확인하고 규칙별 대표 예제와 필요한 경계·실패 사례를 작성한다.
- 결과물은 `.feature` 시나리오와 근거의 출처, 미확정 사항이다. 초안이나 본문만 요청한 경우 요청된 형식으로 전달한다.
- 시나리오 작성만으로 제품 코드, step definition, E2E 자동화, 테스트 러너 설치를 수행하지 않는다. `.feature` 파일의 문법 확인과 실제 동작 검증을 구분한다.

## 맥락과 근거

- 적용되는 `AGENTS.md`, 기여 지침, 기존 명세 위치와 언어·태그·용어 관례를 확인한다. 사용자 지침과 저장소 규칙을 아래 기본 형식보다 우선한다.
- 관련 링크·문서·이미지는 실제로 확인하고 목적·완료 기준·현재 동작·기대 동작·제외 범위를 추출한다. 코드베이스의 호출자·공개 계약·테스트는 현황 확인에 사용하며, 현재 구현을 새 요구사항의 정답으로 복제하지 않는다.
- 각 업무 규칙과 기대 결과는 제공된 요구사항이나 확인된 계약에 근거한다. 경계값·정책·오류 문구·시간 제한을 임의로 발명하지 않는다. 자료에서 합의된 규칙과 설명용 예제를 구분한다.
- 자료가 충돌하거나 기대 동작이 부족하면 먼저 관련 자료로 확인한다. 해소되지 않은 부분은 미확정 사항으로 남기고 독립적인 시나리오는 작성한다. 대화형 환경에서는 핵심 결정만 질문하고, CI에서는 기다리지 않고 부족한 근거와 다음 확인 방법을 반환한다.
- 미확정 정책을 확정된 `Then`으로 작성하지 않는다. 저장소에 초안 구분 규칙이 있으면 따르고, 없으면 Feature 설명이나 주석에 열린 질문을 기록한다. 임의의 `@pending` 태그만으로 실행이 차단된다고 가정하지 않는다.

## 규칙과 시나리오 선정

- 기능의 목적 → 업무 규칙 → 구체적 예제 순서로 정리한다. 주요 정상 흐름, 중요한 거절·실패·복구, 경계와 규칙 간 충돌을 우선한다.
- 하나의 시나리오는 하나의 설명 가능한 행동과 결과를 담는다. 모든 코드 분기나 입력 조합을 기계적으로 나열하지 않는다.
- 숫자 규칙이 있다면 임계값 바로 아래·경계·바로 위에서 결과가 어떻게 달라지는지 확인한다. 권한·상태·시간 등은 결과를 바꾸는 조건만 포함한다.
- 시간·무작위·외부 응답에 의존하면 판단 가능한 조건을 명시한다. 랜덤 추천은 허용된 후보와 제약을 검증하는 결과로 표현하며 명세에 없는 분포나 특정 추첨 결과를 요구하지 않는다.
- 시나리오는 서로 독립적으로 이해할 수 있어야 한다. 앞선 시나리오의 실행이나 데이터에 의존하지 않는다.
- 기존 시나리오와 의미가 같으면 재사용·보완한다. 요구사항 변경 시 영향받는 예제와 관련 명세의 불일치를 확인하되, 요청 밖의 문서를 임의로 새 정책에 맞춰 덮어쓰지 않는다.

## Given–When–Then 작성

- `Given`: 행동 이전의 유의미한 상태·조건.
- `When`: 사용자 또는 외부 시스템의 행동·사건.
- `Then`: 사용자나 외부 시스템이 관찰할 수 있는 결과. “정상 처리된다”처럼 판정 불가능한 표현을 피한다.
- `And`·`But`로 같은 단계의 조건이나 결과를 이어 쓴다. 단계 수를 맞추기 위해 중요한 결과를 빼거나 무관한 행동을 연결하지 않는다.
- 버튼 좌표·CSS selector·내부 state·비공개 함수명보다 업무 용어와 사용자 행동으로 표현한다. UI 자체가 요구사항이면 필요한 화면 동작을, API 계약이면 응답·상태처럼 외부에서 관찰 가능한 결과를 구체적으로 적는다.
- 같은 규칙의 입력·결과만 달라지면 `Scenario Outline`과 `Examples`로 묶는다. 서로 다른 규칙을 거대한 표 하나에 섞지 않는다.
- `Background`는 해당 범위의 모든 시나리오에 실제로 공통인 짧은 전제만 담는다. 성공 전제를 넣은 뒤 실패 시나리오에서 반대로 덮어쓰지 않는다.
- `Rule`은 관련 예제를 업무 규칙별로 묶을 때 사용한다. Data Table은 한 단계의 구조화된 데이터, `Examples`는 시나리오 반복 입력으로 구분한다.

## 저장 형식과 예시

- 저장소의 기존 위치·명명·Gherkin 언어를 따른다. 별도 규칙이 없으면 `specs/scenarios/<기능명>.feature`에 영문 키워드와 한국어 제목·단계를 사용하고 두 칸으로 들여쓴다. 한 파일에는 하나의 `Feature`를 둔다.
- 제목은 `권한이 없는 사용자의 수정 요청을 거부한다`처럼 조건과 결과를 드러낸다. 필요한 출처는 Feature 설명이나 시나리오 앞 주석에 실제 URL·문서 위치로 기록한다. 로컬 절대 경로나 존재하지 않는 티켓 번호를 공유 문서에 넣지 않는다.
- 제품의 행동 명세는 구현 완료 후에도 유지한다. 임시 구현 계획과 구분하며 실제 요구사항 변경에 맞춰 갱신한다.
- 작성 전 [시나리오 예시](references/examples.md)를 참고한다. 예시의 정책을 대상 프로젝트의 요구사항으로 가져오지 않는다.

## 검토와 결과 전달

- 규칙의 출처, 전제의 일관성, 관찰 가능한 결과, 독립성, 중복·누락, 경계 예제와 Outline 변수·표 열의 일치를 확인한다.
- 문법 통과를 제품 동작 통과로 보고하지 않는다. step definition이 없거나 구현이 미완료이면 자동화·구현 상태를 별도로 기록한다.
- 작성·수정한 파일, 다룬 규칙과 주요 예제, 실제 수행한 검사, 남은 질문을 한국어로 보고한다. 요청 없이 커밋·push·이슈 등록을 수행하지 않는다.
