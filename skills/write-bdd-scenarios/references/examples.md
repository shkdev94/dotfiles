# 시나리오 예시

아래 정책은 작성 방식을 설명하기 위한 가상 요구사항이다. 실제 작업에는 합의된 규칙과 값만 사용한다.

## 경계값을 하나의 규칙으로 표현

가정한 요구사항: 주문 금액이 50,000원 이상이면 배송비는 0원, 미만이면 3,000원이다.

```gherkin
Feature: 주문 배송비 안내
  주문 금액에 따른 배송비를 결제 전에 안내한다.

  Scenario Outline: 무료배송 기준에 따라 배송비를 표시한다
    Given 주문 금액이 <주문금액>원이다
    When 사용자가 결제 예정 금액을 확인한다
    Then 배송비가 <배송비>원으로 표시된다

    Examples:
      | 주문금액 | 배송비 |
      | 49999    | 3000   |
      | 50000    | 0      |
      | 50001    | 0      |
```

배송 지역이나 쿠폰 예외가 명세에 없다면 추가하지 않는다. 규칙 간 우선순위가 별도로 주어지면 그 상호작용은 별도 예제로 표현한다.

## 실패 상태와 복구 결과

가정한 요구사항: 오프라인에서는 마지막 추천과 조회 시각을 표시하며, 저장된 추천이 없으면 오프라인 안내를 표시한다.

```gherkin
Feature: 오프라인 추천 확인

  Background:
    Given 네트워크가 오프라인 상태이다

  Scenario: 저장된 추천을 조회 시각과 함께 표시한다
    Given 마지막으로 받은 추천과 조회 시각이 저장되어 있다
    When 사용자가 추천 화면을 연다
    Then 마지막으로 받은 추천이 표시된다
    And 저장된 조회 시각이 표시된다

  Scenario: 저장된 추천이 없으면 오프라인 상태를 안내한다
    Given 저장된 추천이 없다
    When 사용자가 추천 화면을 연다
    Then 오프라인 안내가 표시된다
```

`Background`에 저장된 추천이 있다는 조건을 넣으면 두 번째 시나리오와 충돌한다. 캐시 라이브러리·내부 함수 호출은 이 행동 명세에 필요하지 않다.

## 구현 절차 대신 외부 결과

- 구현에 결합된 표현: `When 사용자가 .submit-button을 클릭한다` → `Then isSubmitting이 false가 된다`.
- 행동을 설명하는 표현: `When 사용자가 유효하지 않은 이메일로 가입을 요청한다` → `Then 이메일 형식 오류가 표시된다`.

오류 문구가 명세로 확정되었을 때만 정확한 문자열을 적는다. 계정 생성 금지나 입력 보존도 합의된 계약이면 추가 결과로 명시한다. 제품이 실제로 그렇게 동작하는지는 별도의 실행 검증이 필요하다.
