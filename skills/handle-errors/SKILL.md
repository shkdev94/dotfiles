# 오류와 예외 처리

## 목표와 역할

호출자가 예상 가능한 실패에 대응할 수 있게 계약을 드러내고, 프로그램 결함이 정상적인 도메인 결과로 숨겨지지 않게 한다. 실패의 의미와 처리 책임을 분리해 사용자 안내, 복구, 진단이 정확하게 이루어지도록 구현하는 것이 이 스킬의 역할이다.

- 입력은 연산의 요구사항과 실패 조건, 기존 오류 타입과 호출자, 프레임워크의 실패 처리 계약, 관련 이슈·로그·테스트다.
- 실패를 분류하고 표현 방식, 변환 경계, 처리 주체, 재시도와 취소 정책을 정리해 요청 범위에서 구현·검증한다.
- 결과물은 명확한 실패 계약과 처리 코드, 관련 검증 결과, 복구할 수 없는 상황과 남은 제약이다.
- 모든 연산을 Result로 바꾸거나 기존 예외 체계를 전면 교체하지 않는다. 새 오류 라이브러리 도입, 관련 없는 리팩터링, 커밋·PR 생성·배포로 작업을 확대하지 않는다.
- `write-good-code`의 일반 구현 원칙을 오류 처리 관점에서 구체화한다. 이슈 구현·테스트 작업과 함께 사용할 수 있지만 별도 스킬의 설치나 실행을 전제로 하지 않는다.

## 실패의 의미부터 분류하기

실패가 예상되는지, 일시적인지, 어느 계층에서 복구할 수 있는지는 서로 다른 질문이다. 예외 클래스나 HTTP 상태 코드만으로 분류하지 말고 연산의 계약과 맥락을 확인한다.

- **예상 가능한 도메인 실패:** 입력 검증 실패, 재고 부족, 결제 거절, 지원하지 않는 포맷 등. 호출자가 구분해 처리할 필요가 있는 결과로 표현한다.
- **운영·외부 의존성 실패:** 네트워크 단절, 타임아웃, 서비스 장애, 자원 부족 등. 곧바로 버그로 단정하지 않는다. 연산과 경계에 따라 재시도·실패 응답·운영 경보가 필요할 수 있다.
- **취소:** 사용자 취소, 요청 종료, 상위 작업 취소 등. 기존 취소 메커니즘을 보존하고 일반 오류나 재시도 대상으로 바꾸지 않는다.
- **프로그램 결함·불변 조건 위반:** 도달 불가능해야 하는 상태, 내부 계약 위반 등. 도메인 실패나 성공 기본값으로 숨기지 않고 적절한 오류 경계로 전파한다.

예를 들어 사용자가 지정한 파일의 부재와 필수 배포 설정의 부재는 의미가 다르다. 후자는 시작 단계에서 명확하게 실패해야 할 수 있지만, 모든 예외가 전체 프로세스 종료를 뜻하지는 않는다. 요청·작업·컴포넌트 중 안전하게 격리 가능한 실패 단위와 유지해야 할 일관성을 판단한다.

## 실패 계약 표현하기

- 호출자가 구분해야 하는 실패를 타입·시그니처·문서·기존 오류 규약으로 드러낸다. 실패 분류는 복구나 사용자 대응이 실제로 달라지는 수준으로 구성한다.
- 언어와 저장소에서 Result, 오류 반환값, 검사되는 예외, 명시적 throws 등을 사용하는 방식을 우선 따른다. 메커니즘 자체보다 호출자가 실패를 인지하고 처리할 수 있는지가 중요하다.
- Result를 채택하는 경계에서는 성공 데이터와 오류를 구분하는 구조를 사용한다. 실패하지 않는 순수 함수까지 감싸거나 의미 없는 unwrap 계층을 추가하지 않는다.
- Result는 모든 실패 처리를 자동으로 보장하지 않는다. 반환값을 무시할 수 있는지, 라이브러리나 런타임 예외가 별도로 전파되는지 확인한다. 타입 검사가 있더라도 외부 입력 검증을 생략하지 않는다.
- 오류 종류별 분기가 필요한 경우 언어가 지원하는 완전성 검사나 명시적 누락 검증을 사용한다. 새 오류 종류가 추가될 때 영향을 받는 호출자를 확인한다.
- 오류 코드와 필요한 맥락을 안정적으로 유지한다. 사용자에게 보여줄 문구와 내부 원인 정보를 구분하고 메시지 문자열 비교로 오류 종류를 판별하지 않는다.

## catch와 변환 경계

- catch는 해당 실패를 처리하거나, 계약에 맞게 변환하거나, 정리 후 전파할 책임이 있는 위치에 둔다. 모든 함수나 최상위 한 곳이라는 고정 규칙을 적용하지 않는다.
- 외부 라이브러리의 알려진 실패는 어댑터 경계에서 해당 연산의 실패 계약으로 변환한다. 문서화된 오류 코드·타입·응답 정보를 사용하고 문자열 추측을 피한다.
- try 범위는 처리하려는 실패가 발생하는 구간으로 좁힌다. 네트워크 실패를 잡는 범위에 무관한 변환·도메인 계산까지 넣어 내부 버그를 네트워크 오류로 오인하지 않게 한다.
- 분류되지 않은 예외는 기본적으로 원인과 스택을 보존해 상위 오류 경계로 전파한다. 언어가 요구하면 원인 연결을 사용한다. 오류를 감싸면서 원래 맥락을 잃지 않는다.
- 경계 계약상 포괄적인 내부 오류로 변환해야 한다면 진단용 원인을 보존하고 예상 가능한 도메인 실패와 구분한다. 알 수 없는 오류를 무조건 재시도 가능하거나 사용자 잘못인 결과로 바꾸지 않는다.
- 빈 catch, 실패 시 무조건 빈 배열·null·성공 값 반환, 오류 로그만 남기고 정상 흐름을 계속하는 처리를 피한다. fallback은 실제로 정의된 동작이고 호출자가 그 상태를 알아야 하는지 판단한 경우에만 사용한다.
- 자원 정리는 언어의 finally·defer·스코프 기반 자원 관리 등을 사용한다. 정리 중 발생한 오류로 최초 실패가 사라지지 않도록 해당 환경의 규약을 따른다.

## 프레임워크와 연결하기

- 프레임워크가 예외나 실패한 비동기 작업으로 오류 상태를 판단하면 그 경계를 따른다. Result의 실패 값을 그대로 반환해 성공 데이터로 인식시키지 않는다.
- 내부 실패 표현과 HTTP 응답·UI 상태·작업 결과 사이의 변환은 책임 있는 어댑터에서 수행한다. 같은 변환을 계층마다 반복하지 않는다.
- 외부 상태 코드를 업무 의미로 바꾸기 전에 요청 맥락을 확인한다. 예를 들어 모든 404를 동일한 도메인 객체의 부재로 해석하지 않는다.
- 프레임워크의 제어 흐름용 예외와 취소 신호를 일반적인 내부 오류로 감싸지 않는다. 관련 동작이 불확실하면 설치 버전의 공식 문서를 확인한다.

## 복구·재시도·관측

- 오류를 감지하는 계층과 복구 결정을 내리는 계층을 구분한다. 권한이나 정보가 없는 하위 계층에서 임의로 재시도·사용자 안내 정책을 결정하지 않는다.
- 재시도는 일시적인 실패이며 중복 실행이 안전할 때만 한다. 횟수·시간 제한, 지연, 취소 전파를 정하고 여러 계층의 중첩 재시도를 피한다.
- 타임아웃은 원격 작업의 실패나 롤백을 보장하지 않는다. 결제·생성 같은 연산에서는 완료 상태 확인과 멱등성 등 중복 효과를 막는 계약을 확인한다.
- 부분 실패 시 유지해야 할 상태를 확인하고 필요에 따라 트랜잭션·보상·원자적 전환 등 기존 방식을 사용한다. 오류를 잡았다는 이유로 계속 실행해도 안전하다고 판단하지 않는다.
- 예상 가능한 거절을 모두 장애 수준으로 기록하지 않는다. 프로그램 결함과 운영 장애는 담당 경계에서 원인과 상관관계를 추적할 정보를 남기고 중복 로그를 피한다.
- 사용자 응답에는 대응 가능한 설명을 제공하되 스택·자격 증명·민감한 입력을 노출하지 않는다. 내부 진단에는 필요한 맥락만 보존한다.

## 검증과 결과 전달

- 중요한 예상 실패가 올바른 타입·응답·UI 동작으로 연결되는지 검증한다. 실패 후 데이터와 상태가 계약대로 보존되는지도 확인한다.
- 예상 실패를 처리하는 catch에 뜻밖의 내부 오류를 주었을 때 정상 도메인 실패로 변환되지 않는지 검증한다. 원인 보존과 최종 오류 경계를 확인한다.
- 관련될 때 취소, 타임아웃, 재시도 종료, 부분 실패와 자원 정리를 검증한다. 실행 시간에 의존하는 고정 sleep으로 테스트하지 않는다.
- 기존 호출자의 성공 경로와 실패 처리가 호환되는지 확인한다. 오류 타입 추가·반환 방식 변경이 있으면 영향을 받는 경계를 명시한다.
- 실제 검증 결과와 변경한 실패 정책을 보고한다. 정책이 미확정이면 추측으로 복구 동작을 만들지 말고 필요한 결정만 설명한다.

## 유용한 명령어

변수는 확인한 실제 값으로 채운다. 필요한 명령만 선택하고, 설치 버전과 저장소의 실행 규칙을 따른다.

```bash
# 오류 계약과 호출자·관련 테스트 검색
rg -n -F -- "$ERROR_TYPE" "$SOURCE_DIR"
rg -n -F -- "$OPERATION" "$SOURCE_DIR"
rg --files -g '*test*' -g '*spec*'
# 실패 경로 변경 검토
git diff --check
git diff -- "$FILE_PATH"
```

검색은 후보를 찾는 용도이며 호출자와 오류 경계의 문맥을 직접 읽는다. 로그는 필요한 시간·요청 범위만 확인하고 민감한 원문이나 환경 변수 전체를 출력하지 않는다. 실패 시나리오는 저장소의 대상 테스트 명령으로 검증하며, 실제 운영 서비스에 오류·재시도·취소를 발생시켜 확인하지 않는다.
