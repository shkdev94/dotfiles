# PR 작성

## 목표와 역할

작업 브랜치의 변경과 검증 결과, 관련 작업의 맥락을 입력받아 리뷰 가능한 GitHub PR을 생성하거나 갱신한다. 변경 목적과 범위, 검증 결과 및 후속 작업을 리뷰어가 이해할 수 있도록 정리한다. 결과물은 실제 PR URL과 정확한 base·head, 제목·본문이다.

## 진행 방식

- 저장소 지침과 PR 템플릿, 현재 브랜치·커밋·원격 및 기존 관련 PR을 확인한다. 명시적인 사용자·저장소 규칙과 필수 템플릿을 아래 기본 형식에 우선한다.
- base는 사용자 지정과 작업 의존성을 따른다. 지정이 없으면 저장소 기본 브랜치를 조회하며 `main`으로 가정하지 않는다. 스택은 아래 생성·갱신 절차를 따른다.
- base 대비 커밋과 전체 diff를 읽어 이번 PR의 목적·범위·검증 결과를 확인한다. 미커밋 변경을 PR에 포함됐다고 설명하지 않는다.
- 미커밋 변경이 있으면 PR에 포함될 변경과 구분한다. 커밋까지 요청받았다면 해당 범위를 먼저 커밋하고, PR에는 실제 게시된 커밋만 반영한다.
- PR 생성 요청에는 대상 브랜치를 게시하기 위한 push를 포함한다. 원격·head 저장소를 확인하고 필요한 커밋을 push한다. 이력을 임의로 재작성하지 않는다.
- 같은 작업의 PR이 있으면 중복 생성하지 않고 갱신한다. 초안·리뷰어·라벨 등은 요청과 저장소 규칙에 따른다. PR을 임의로 병합하거나 배포하지 않는다.

## Stacked PR 생성·갱신

작업 단위와 의존 순서가 정해진 브랜치들을 PR로 연결한다. 분할되지 않은 큰 변경을 임의로 재구성하지 않는다. 스택 생성 요청에 필요한 브랜치나 의존 순서가 불명확하면 현재 커밋과 기존 PR을 확인하고 필요한 결정만 질문한다.

1. 단계별 목적, head 브랜치, 선행 단계와 기존 PR을 확인한다. 브랜치 이름이나 생성 시각만으로 의존 순서를 추정하지 않는다. 독립적인 변경은 별도 PR로 다룬다.
2. 첫 PR의 base는 기본 또는 지정된 시작 브랜치로, 후속 PR의 base는 바로 앞 단계의 head 브랜치로 설정한다. 예를 들어 `시작 브랜치 ← PR 1 head ← PR 2 head`라면 PR 2의 base는 PR 1 head다.
3. 각 base 대비 diff와 커밋을 확인하여 해당 단계의 추가 변경만 포함되는지 검토한다. 선행 변경이 중복되거나 필요한 변경이 빠졌다면 원인을 해결한 뒤 게시한다. 이력 재작성이 필요하면 요청 범위와 저장소 규칙을 확인한다.
4. 선행 단계부터 브랜치를 push하고 PR을 생성·갱신한다. `gh stack`을 사용할 때는 설치된 도구의 종류·버전·도움말과 저장소의 스택 관례를 확인하고 지원되는 명령만 사용한다. 도구가 없거나 적합하지 않으면 명시적인 base·head로 일반 PR을 생성한다.
5. 각 PR 본문에 단계별 범위, 선행·후속 PR 링크와 리뷰 순서를 적는다. 후속 PR 생성 후 앞선 본문의 링크를 갱신하고, 아직 없는 PR의 URL을 만들어 쓰지 않는다. 이슈 연결은 아래 `Closes`·`Refs` 판단 기준을 적용한다.
6. 생성·갱신 후 실제 base·head와 diff를 다시 확인한다. 실행 환경에서 여러 브랜치 게시가 제한되면 가능한 단계와 미생성 단계를 구분해 보고한다. 나머지를 큰 PR 하나로 합쳐 대신 게시하지 않는다.

선행 PR 병합 후 갱신 요청에서는 후속 PR의 base와 diff를 다시 확인한다. 특히 squash·rebase 병합은 base만 바꾸면 선행 변경이 중복될 수 있으므로 실제 커밋과 변경 반영 상태를 확인한다. 필요한 rebase·스택 동기화·강제 push는 요청 범위와 저장소 규칙 안에서 수행하고, 수행할 수 없는 갱신은 대상 PR과 영향을 보고한다. 선행 변경을 수정했다면 영향받는 단계의 검증 결과도 다시 확인한다.

## PR 제목

작성 형식은 다음 우선순위로 결정한다. 실행 환경의 필수 제약은 준수한다.

1. 이번 작업에서 사용자가 명시한 지침
2. 적용되는 `AGENTS.md`, 기여 지침, 필수 템플릿과 설정
3. 최근 유사 작업 여러 건에서 확인되는 일관된 저장소 관례
4. 위 기준으로 정해지지 않은 항목에 대한 아래 기본 형식

관례는 단일 사례나 자동 생성된 기록만으로 단정하지 않는다. 대상 경로·작업 유형에 맞는 사례를 비교하고, 명시된 규칙과 충돌하면 명시된 규칙을 따른다. 형식·언어·분류 등 저장소에서 정한 항목을 스킬의 기본값으로 덮어쓰지 않는다.

PR 제목은 다음 형식의 한 줄로 작성한다.

```text
[type] - 한국어 변경 요약
```

- `feat`: 새로운 기능 추가
- `fix`: 버그 수정
- `hotfix`: 긴급 버그 수정
- `refactor`: 동작 변경 없이 구조 개선
- `chore`: 설정, 의존성, 유지보수
- `docs`: 문서 수정
- `style`: 동작 변경 없는 코드 스타일·포맷팅
- `release`: 배포 준비

PR 제목은 해당 PR 전체의 목적을 요약한다. `코드 수정`, `작업`, `변경사항 반영`처럼 모호한 표현을 피한다. 스택에서도 각 PR의 구체적인 목적이 제목에 드러나게 한다.

```text
[feat] - 조직 멤버 초대 기능 추가
[fix] - 검수 완료 후 수정 값 표시 오류 수정
[chore] - 이슈 구현 스킬 추가
```

## PR 본문

아래 형식을 사용하고 안내 문구를 실제 변경 내용으로 대체한다. 후속 작업이 없으면 해당 섹션을 생략한다.

```markdown
## 변경 내용

- 주요 변경과 달라지는 동작을 설명한다.
- 파일 목록보다 무엇을 어떻게 바꿨는지 작성한다.

## 배경

변경이 필요한 이유와 해결하려는 문제를 설명한다.

Closes #이슈번호

## 검증

- 실행한 테스트·빌드·린트 명령과 결과를 기록한다.
- 실행하지 못한 검증은 완료한 검증과 구분한다.

## 후속 작업

- 남은 작업이나 검증, 필요한 이유를 기록한다.
```

- 연결된 이슈가 없으면 이슈 연결 문구를 생략하며, PR 작성을 위해 새 이슈를 만들지 않는다. 이슈가 있으면 본문과 관련 댓글의 완료 기준을 확인하고 `#이슈번호`를 실제 이슈 번호로 바꾼다.
- **`Closes #번호`**: 이 PR이 병합되면 이슈의 요구사항과 필수 검증이 모두 충족되는 경우 사용한다. 이슈 전체를 해결하는 단일 PR에는 `Closes`를 사용한다. 이미 병합된 선행 작업과 이번 변경으로 이슈가 완료되는 마지막 PR도 동일하다. 이슈 범위 밖의 선택적 개선이나 단순히 리뷰·병합을 기다린다는 이유로 `Refs`로 바꾸지 않는다.
- **`Refs #번호`**: 이번 PR이 이슈의 일부만 구현하여 필수 작업이 남거나, 해당 이슈를 해결하는 것이 아니라 배경·관련 작업으로 참조하는 경우 사용한다. 본문에 남은 요구사항 또는 참조 이유를 구체적으로 적는다. 단일 PR이어도 부분 구현이면 `Refs`가 맞지만, 단순히 종료 여부를 검토하지 않았다는 이유로 기본값처럼 사용하지 않는다.
- 이슈가 여러 개면 각 이슈의 완료 여부를 따로 판단한다. 예를 들어 이슈 123을 완료하고 이슈 456의 일부만 구현했다면 `Closes #123`과 `Refs #456`을 함께 적는다. PR 생성·갱신 전에 각 연결 문구가 실제 완료 범위와 일치하는지 확인한다.
- 스택 생성 절차에서 확인한 단계별 범위, PR 링크와 리뷰 순서는 배경 섹션에 기록한다.
- 후속 작업에는 남은 구현·통합 검증과 필요한 이유를 기록한다. 현재 PR의 필수 완료 조건이 남았다면 완료로 보고하지 않는다.
- GitHub의 이슈 자동 종료 조건과 실제 base를 확인한다. 기본 브랜치 이외를 대상으로 하는 PR은 `Closes`만으로 병합 시 이슈가 자동 종료된다고 가정하지 않는다. 이 경우 `Refs`로 바꿔 문제를 숨기지 말고, 기본 브랜치로 통합할 PR에서 종료 문구를 확인하는 등 필요한 종료 조치를 후속 작업과 결과에 명시한다. 마지막 스택 PR이라는 이유만으로 전체 변경이 기본 브랜치에 반영됐다고 판단하지 않는다.
- 구현 도중 범위가 바뀌면 제목과 본문을 최종 변경 기준으로 갱신한다. 폐기한 접근이나 대화 이력은 판단에 필요한 경우에만 포함한다.

## 결과 전달

- 생성·갱신 후 PR URL, base, head, 제목, 본문과 diff를 다시 확인한다. push 성공이나 PR 작성 화면의 링크만으로 생성 완료를 보고하지 않는다.
- PR URL과 변경 요약, 실제 검증 결과, 남은 작업을 한국어로 보고한다. 여러 PR이면 각 목적과 의존 순서를 함께 적는다.
- 권한·환경 문제로 실패하면 현재 완료 상태와 필요한 다음 조치를 명확히 알린다.

## 유용한 명령어

변수는 확인한 실제 값으로 채운다. 생성·갱신과 스택 명령은 필요한 경우에만 선택한다.

```bash
# 기본 브랜치와 기존 PR 확인
gh repo view "$OWNER_REPO" --json nameWithOwner,defaultBranchRef,viewerPermission
gh pr list --repo "$OWNER_REPO" --head "$HEAD_BRANCH" --state open
git log --oneline "$BASE_REF..$HEAD_REF"
git diff "$BASE_REF...$HEAD_REF"

# 브랜치 게시와 PR 생성
git push -u "$REMOTE" "$HEAD_BRANCH"
gh pr create --repo "$OWNER_REPO" --base "$BASE_BRANCH" --head "$HEAD_SELECTOR" \
  --title "$TITLE" --body-file "$BODY_FILE"

# 기존 PR 갱신과 결과·CI 확인
gh pr edit "$PR_URL" --title "$TITLE" --body-file "$BODY_FILE"
gh pr view "$PR_URL" --json url,title,body,baseRefName,headRefName,state
gh pr diff "$PR_URL"
gh pr checks "$PR_URL"

# 스크린샷 업로드: 반환된 Markdown을 본문 파일에 반영
gh attach "$SCREENSHOT_PATH" --repo "$OWNER_REPO" --markdown

# 공식 gh-stack 확장: 조회와 이미 생성된 PR의 스택 연결
gh stack view --json
gh stack link --base "$BASE_BRANCH" "$FIRST_PR_URL" "$SECOND_PR_URL"

# 이미 관리 중인 로컬 스택을 게시하는 대안
gh stack submit
```

일반 PR 생성 후 `link`로 연결하거나 기존 로컬 스택을 `submit`하는 경로 중 상황에 맞는 방식을 선택한다. fork의 head 지정과 스택 명령의 push·base 변경 효과는 [명령별 사용 조건](references/commands.md)을 먼저 확인한다.
