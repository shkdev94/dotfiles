# 병합된 PR 정리

## 목표와 역할

병합이 완료되어 더 이상 필요 없는 PR 작업 브랜치와 워크트리를 정리한다. 사용자 작업과 후속 PR을 보존하면서 요청된 PR에 속한 자원만 제거하는 것이 이 스킬의 역할이다.

- 입력은 GitHub PR URL이다. 로컬 저장소는 현재 작업 공간과 원격 URL에서 찾고, 확정할 수 없을 때만 경로를 묻는다. 로컬 정리를 위해 새 저장소를 clone하지 않는다.
- PR 상태·head 커밋·저장소, 로컬 브랜치·워크트리 상태와 의존성을 조사하고 삭제 가능한 대상을 정리한다.
- 결과물은 삭제한 원격·로컬 브랜치와 워크트리 목록, 이미 없는 항목, 보존한 항목과 이유다. 한국어로 보고한다.
- 병합·이슈 종료는 수행하지 않는다. 아래 Git 제외 파일 처리 외의 새 커밋·rebase·변경 폐기·stash 생성·다른 PR의 base 변경은 일반 정리 요청만으로 수행하지 않고, 아래의 처리 방식 질문에 대한 명시적인 답변이 있을 때 승인된 범위에서만 수행한다. 전체 저장소의 오래된 브랜치를 일괄 정리하지 않는다.
- 사용자의 PR 정리 요청은 검증된 대상의 삭제를 허용한다. 정상적인 대상마다 반복 승인을 요구하지 않는다. 아래 Git 제외 파일을 제외한 미커밋 변경·추가 커밋·다른 PR이나 로컬 브랜치의 의존성이 있으면 반드시 처리 방식을 묻는다. 답변 전에는 해당 항목과 이에 의존하는 자원을 변경하지 않고, 독립적으로 정리 가능한 나머지는 진행한다.

## 대상 식별

1. PR URL의 호스트·저장소·번호를 확인하고 해당 호스트의 인증된 `gh`로 PR을 조회한다. 대상 저장소의 적용 지침을 읽는다.
2. 상태가 `MERGED`이고 병합 시각이 존재하는지 확인한다. `CLOSED`이지만 병합되지 않은 PR이나 열린 PR은 정리하지 않는다.
3. base 저장소·브랜치, head 저장소·브랜치, 병합된 PR의 최종 head SHA, 병합 커밋을 기록한다. 원격 브랜치의 현재 SHA를 병합 당시 SHA 대신 사용하지 않는다. 확인할 수 없으면 해당 삭제를 보류한다.
4. 로컬 원격의 fetch·push URL과 실제 저장소를 대조한다. `origin`이라고 가정하지 않는다. fork PR은 head 저장소가 별도라는 점을 반영하며, base 저장소의 동명 브랜치를 지우지 않는다.
5. `git worktree list --porcelain`로 동일한 Git 공통 디렉터리에 속한 워크트리를 확인한다. 브랜치 이름만이 아니라 upstream·원격·커밋과 PR 맥락으로 로컬 대상을 연결한다. detached 워크트리는 SHA 일치만으로 소유 관계를 단정하지 않는다.

로컬 저장소를 찾지 못해도 원격 대상이 명확하면 원격 검사와 정리는 진행할 수 있다. 로컬 항목은 확인하지 못했다고 보고한다. API 권한 오류나 네트워크 실패를 자원이 이미 삭제된 것으로 처리하지 않는다.

## 삭제 전 판단 기준

- head가 기본 브랜치, PR의 base, 보호된 브랜치, 또는 저장소 지침상 유지해야 하는 공유·릴리스 브랜치이면 보존한다. 기본 브랜치는 해당 저장소 메타데이터에서 조회한다.
- 원격 head tip과 로컬 후보 tip을 각각 병합된 PR의 최종 head SHA와 비교한다. 정확히 일치하는 대상을 기본 정리 대상으로 삼는다. 추가 커밋·분기·재사용이 있으면 커밋과 영향을 확인해 처리 방식을 반드시 묻는다. 출처 불명 상태는 추가 확인하거나 필요한 정보를 질문한다. 로컬과 원격은 독립적으로 판단한다.
- 단순히 기본 브랜치에 조상으로 포함되지 않는다는 이유만으로 미병합이라 판단하지 않는다. squash·rebase 병합에서는 SHA가 달라진다. 반대로 패치가 비슷하거나 PR이 병합됐다는 이유만으로 추가 커밋을 삭제하지 않는다.
- 대상 head 저장소에서 해당 브랜치를 base로 쓰는 열린 PR과, 같은 head 저장소·브랜치를 사용하는 다른 열린 PR을 확인한다. 페이지를 모두 확인하고 실제 저장소 정체성을 비교한다. 의존성이 있으면 관련 PR 링크와 영향 범위를 제시하고 처리 방식을 반드시 묻는다. 조회가 불완전하면 조회를 보완하기 전에는 삭제하지 않는다.
- 로컬 upstream과 기존 stack 메타데이터에서 후속 브랜치 의존성을 확인한다. 후속 작업이 있으면 의존 브랜치와 정리 영향을 제시하고 처리 방식을 반드시 묻는다. 의존 관계를 해소하는 `gh stack sync`, rebase, retarget은 사용자가 구체적인 처리 방식을 승인한 뒤에만 수행한다.
- 워크트리의 staged·unstaged·untracked 파일과 Git 제외 파일을 구분한다. 제외 파일은 아래 기준으로 처리하며, 존재한다는 이유만으로 미반영 작업으로 판단하거나 질문하지 않는다. 파일 내용이나 비밀 값은 출력하지 않는다.
- 워크트리가 locked이거나 merge·rebase·cherry-pick·bisect 중이면 보존한다. 서브모듈·중첩 저장소의 상태를 안전하게 확인할 수 없거나 제거에 강제가 필요하면 보존한다.
- 다른 사용자·에이전트·터미널·서버가 사용하는 워크트리는 보존한다. 현재 실행 중인 작업의 cwd이거나 수명에 연결된 워크트리는 단순히 셸 위치를 옮기는 것으로 제거 가능하다고 판단하지 않는다. 사용 여부가 불확실하면 해당 경로만 보류한다.
- 메인 워크트리 자체는 삭제하지 않는다. 그곳에서 대상 브랜치가 체크아웃되어 있으면 깨끗하고 사용 중이지 않은 경우에만 검증된 기존 기본 브랜치로 전환한다. 다른 워크트리에서 기본 브랜치를 사용 중이면 억지로 전환하거나 detach하지 않는다.

## Git 제외 파일 처리

Git에서 무시되는 파일은 미반영 커밋이 아니다. 실제 ignore 규칙과 추적 여부를 확인하고 다음과 같이 처리한다. 파일명만으로 제외하거나, 추적 중인 파일의 변경을 무시하지 않는다.

- **재생성 가능한 파일**: `node_modules`, `build`, `dist`, `.next`, `coverage` 등 의존성·빌드 결과·캐시로 확인된 제외 파일은 질문 없이 워크트리와 함께 제거한다. 해당 경로에 직접 작성한 파일이나 로컬 데이터가 섞여 있으면 그 부분은 별도로 판단한다.
- **로컬 환경 설정**: Git에서 제외된 `.env`와 `.env.*`는 위 재생성 파일과 동일하게 백업이나 질문 없이 워크트리와 함께 제거한다. 추적 중인 환경 설정 파일의 변경에는 이 예외를 적용하지 않는다. 비밀 값을 출력하거나 Git에 추가하지 않는다. 심링크는 링크 자체만 제거하고 외부 원본은 삭제하지 않는다.
- **그 밖의 데이터**: 위 정리 대상 외의 로컬 DB, 직접 작성한 비추적 소스, 재생성 여부가 불명확한 파일은 ignore 여부와 관계없이 처리 방식을 묻는다.

이 예외는 삭제가 확정된 대상 워크트리에만 적용한다. 유지할 워크트리의 파일을 따로 청소하지 않는다.

## 사용자 결정이 필요한 항목

- 위 Git 제외 파일 처리로 해결되지 않는 미커밋 변경·비추적 데이터, PR 이후 추가 커밋, 다른 PR·브랜치의 의존성은 **발견하면 반드시 질문**한다. 최종 보고에 보존했다고 적는 것만으로 질문을 대신하지 않는다.
- 질문 전에 읽기 전용으로 대상 경로·ref·커밋 SHA와 제목·관련 PR 링크를 확인하고, 삭제하면 잃는 작업이나 끊어지는 의존성을 설명한다. 민감한 파일 내용은 노출하지 않는다.
- 미커밋 변경에는 그대로 유지, 지정 위치에 백업 후 정리, 변경 폐기 후 정리 등 실제 가능한 선택지를 제시한다. 추가 커밋에는 브랜치 유지, 별도 보존 브랜치에 커밋을 남긴 뒤 정리, 커밋 폐기 후 정리 등을 제시한다.
- 후속 PR 의존성에는 현재 유지, 선행 변경의 반영을 확인하고 후속 base·stack을 갱신한 뒤 정리 등 가능한 방식을 설명한다. squash 병합 뒤 단순 base 변경만으로 안전하다고 가정하지 않는다.
- 관련 질문은 가능한 한 묶어서 하되, 파일·커밋·PR마다 어떤 선택을 적용하는지 명확히 한다. 답변이 없거나 모호하면 `결정 대기`로 두고 해당 작업을 실행하지 않는다.
- 사용자가 이미 정확히 같은 대상과 손실·영향에 대해 처리 방식을 명시했다면 다시 묻지 않는다. 일반적인 “정리해줘”는 새로 발견한 변경의 폐기나 후속 PR 수정 승인으로 간주하지 않는다.
- 답변 이후 승인한 대상·처리 방식에 한해 수행한다. 백업을 선택했으면 복원 가능한 파일·커밋이 실제로 보존됐는지 확인한 뒤 원본을 정리한다. 변경 폐기를 선택했으면 삭제 직전에 대상 상태를 다시 확인한다.
- 승인 이후 새로운 파일·커밋·의존성이나 다른 영향이 발견되면 해당 부분은 다시 질문한다. 기존 승인을 새로운 손실까지 확대하지 않는다.

## 실행 절차

삭제 전에 [안전한 명령과 검증](references/commands.md)을 읽는다.

1. 정리할 PR, 저장소, 정확한 브랜치·경로와 보존 사유를 간단히 안내한다. 조회한 ref SHA와 워크트리 상태를 각 변경 직전에 다시 확인한다.
2. 대상 linked worktree를 대상 밖의 유효한 저장소 경로에서 `git worktree remove`로 제거한다. 위 기준으로 분류한 Git 제외 파일은 함께 정리한다. 명령이 이 파일들 때문에 거부되면 검증된 해당 파일만 정리한 뒤 재시도한다. 전체 `git clean`이나 강제 워크트리 삭제로 다른 검사 실패를 우회하지 않는다. 사용자가 특정 변경의 폐기를 승인한 경우에만 확인한 대상에 필요한 최소 작업을 수행하며, 광범위한 삭제나 관련 없는 파일 정리는 하지 않는다.
3. 어떤 워크트리에서도 체크아웃되지 않은 로컬 후보 브랜치를 제거한다. 일반 삭제를 우선하며 squash·rebase 병합은 참고 문서의 명시된 조건에서만 처리한다.
4. 원격 브랜치는 확인한 head 저장소의 정확한 ref와 SHA를 조건으로 삭제한다. 원격 상태가 바뀌어 조건부 삭제가 실패하면 재평가하고 무조건 재시도하지 않는다.
5. 삭제된 원격 브랜치의 로컬 추적 ref가 남았으면 해당 ref만 확인해 정리한다. 무관한 ref까지 제거하는 일괄 prune은 수행하지 않는다.
6. 워크트리 목록, 로컬 ref, 원격 ref를 다시 조회해 실제 결과를 확인한다. 일부 단계 실패가 있어도 완료한 단계와 보존한 단계를 구분한다.

이미 없는 대상은 정상적인 결과로 취급한다. 디렉터리가 없고 등록 정보만 남은 워크트리는 오프라인 디스크·공유 경로일 수 있으므로 존재하지 않는다는 이유만으로 제거하지 않는다. `git worktree prune --dry-run --verbose` 결과를 확인하고, 불필요한 등록임이 확인된 요청 대상만 제거될 경우에 한해 prune한다. 무관한 후보가 함께 제거된다면 보류한다.

## 결과 보고

- PR URL과 병합 확인 결과를 적는다. Git 제외 파일을 함께 정리했다면 그 종류를 간단히 알린다.
- 원격 브랜치, 로컬 브랜치, 워크트리 각각을 `삭제`, `이미 없음`, `사용자 선택으로 보존`, `결정 대기`, `안전 조건으로 보존`, `확인 실패`로 구분하고 정확한 이름·경로를 적는다.
- 보존·결정 대기 항목에는 구체적인 이유와 받은 사용자 결정 또는 아직 필요한 결정을 설명한다. 질문이 필요한 항목을 자동 보존 결과로 마무리하지 않는다. 추가 조치가 필요하면 해당 항목에 필요한 작업만 알린다.
- 성공하지 않은 삭제를 완료로 보고하지 않고, 전체 시스템 정리나 PR 병합을 이어서 수행하지 않는다.

## 유용한 명령어

변수는 확인한 실제 값으로 채운다. 삭제 명령은 본문의 병합·파일·의존성 검사가 끝난 대상에만 사용한다.

```bash
# 병합 여부와 정확한 대상 확인
gh pr view "$PR_URL" --json url,state,mergedAt,headRefName,headRefOid,headRepository,headRepositoryOwner,baseRefName,mergeCommit
git worktree list --porcelain
git -C "$WORKTREE" status --porcelain=v1 --untracked-files=all
git -C "$WORKTREE" ls-files --others --ignored --exclude-standard --directory
git ls-remote --heads "$HEAD_REMOTE" "refs/heads/$HEAD_BRANCH"

# 검증된 워크트리와 로컬 브랜치 제거
git -C "$REPO" worktree remove -- "$WORKTREE"
git -C "$REPO" branch -d -- "$LOCAL_BRANCH"

# 확인한 SHA가 그대로인 원격 브랜치만 삭제
git push --force-with-lease="refs/heads/$HEAD_BRANCH:$VERIFIED_REMOTE_SHA" \
  "$VERIFIED_HEAD_PUSH_URL" ":refs/heads/$HEAD_BRANCH"
```

squash·rebase 병합, 원격 ref와 스택 의존성 처리는 [명령별 검증 조건](references/commands.md)을 따른다. 삭제 명령을 조회 명령과 일괄 실행하지 않는다.
