# 변경 사항 검증

## 목표와 역할

변경이 기대 동작과 완료 기준을 충족하는지 실제 검증으로 확인한다. 변경의 영향에 맞는 검사를 선택하고, 기대 결과와 실제 결과를 대조해 통과·실패·미검증을 근거와 함께 전달한다.

- 입력은 사용자 요청과 대화에서 합의한 요구사항, 작업 티켓(예: GitHub 이슈, Jira 티켓), 명세·디자인·이미지 등 제공된 자료, 대상 코드와 변경 사항이다. 실제 제공되거나 연결된 자료를 사용한다.
- 검증 기준과 영향 범위를 확인하고 필요한 테스트·정적 검사·빌드·실행·브라우저 검증을 수행한다. 결과는 한국어로 보고한다.
- 결과물은 완료 기준별 검증 결과, 실행 명령과 환경, 확인된 문제 및 미검증 범위다. 모든 검사를 일괄 실행하는 것을 목표로 하지 않는다.
- 검증 요청만으로 제품 코드를 수정하거나 테스트 체계를 전면 도입하지 않는다. 필요한 임시 검증 스크립트는 만들 수 있지만, 영구 테스트 추가·수정은 요청 범위와 저장소 규칙을 따른다. 외부 게시·배포는 해당 요청이 있을 때 수행한다.

## 기준과 영향 범위

- 적용되는 `AGENTS.md`, 사용자 지침, 실행 스크립트와 CI 설정을 확인한다. 명시된 필수 검사는 유지하고, 아래 실행 설정은 별도 요구가 없는 경우의 기본값으로 사용한다.
- 사용자 자료의 원문과 연결된 문서·이미지를 실제로 확인한다. 기대 동작·완료 기준·재현 절차·제외 범위를 추출하고, 자료의 버전·시점이 검증 대상에 맞는지 확인한다.
- 코드베이스의 구현·타입·공개 계약·호출자·설정·관련 테스트와 diff를 읽는다. PR은 실제 base·head, 로컬 작업은 미커밋 변경을 포함한 지정 범위를 확인한다. 현재 구현이나 현재 테스트의 기대값만을 정답으로 삼지 않는다.
- 기준마다 출처, 확인할 시나리오, 실행 방법과 기대 결과를 연결한다. 정상 동작뿐 아니라 변경과 관련된 경계·실패·회귀 시나리오를 선별한다. 부분 작업과 stacked PR은 해당 단계의 책임과 선행 변경을 기준으로 검증한다.
- 기대 동작이나 자료가 충돌하면 허용된 추가 확인으로 먼저 해소한다. 해소되지 않은 항목은 미확정으로 남기고 독립적인 검증을 진행한다. 대화형 환경에서는 핵심 결정만 질문하고, CI에서는 응답을 기다리지 않고 부족한 근거·영향·다음 확인 방법을 반환한다.

## 검증 선택과 실행

| 변경과 판단 대상 | 검증 방법 |
| --- | --- |
| 계산·변환·도메인 규칙 | 관련 테스트와 의미 있는 경계·실패 입력 |
| 타입·의존성·빌드 설정 | 저장소의 정적 검사·설정 평가·빌드 |
| 실행 도구·서비스 설정 | 빌드 결과와 실제 실행·연결 상태 |
| 웹 UI 동작·화면 흐름 | Playwright headless로 입력·클릭·상태 변화와 결과 확인 |
| 웹 UI 디자인·레이아웃 | 기준 디자인·이미지와 실제 렌더링 대조, 관련 viewport·상태 확인 |
| API·저장 상태와의 연결 | 허용된 테스트 환경에서 응답과 후속 상태 확인 |

- 저장소의 기존 도구·버전과 테스트 명령을 사용하고 관련 범위부터 실행한다. 이후 변경이나 새 실패가 없다면 이미 수행된 유효한 검증을 반복하지 않는다.
- 테스트 통과가 어떤 기준을 검증했는지 확인한다. 빌드·유닛 테스트 성공으로 실제 화면이나 통합 동작까지 검증했다고 보고하지 않는다. 테스트 0개 실행·skip·재시도 후 통과를 첫 실행 성공과 구분한다.
- 변경 후의 코드와 환경을 확인한다. 다른 커밋·빌드·서버를 검증하지 않도록 실행 대상과 반영 상태를 확인하고, 모킹된 범위와 실제 서비스까지 확인한 범위를 구분한다.
- 실패 원인을 제품 결함, 검증 코드 문제, 기존 실패, 환경 제약으로 구분한다. 기대값 약화, snapshot 일괄 갱신, 검사 생략으로 성공을 만들지 않는다.
- 실제 사용자 데이터나 운영 환경에 영향을 주는 동작은 승인된 범위에서만 실행한다. 별도 승인 없이 검증용 입력으로 결제·메일 발송·데이터 삭제를 수행하지 않는다.

## 웹 UI와 디자인 검증

- 웹 UI 검증은 browser-use 대신 Playwright로 수행한다. 기본은 실제 Google Chrome의 `channel: 'chrome'`, `headless: true`, 단일 worker다. 사용자 브라우저 프로필에 연결하지 않고 격리된 테스트 context를 사용한다.
- 영상 녹화와 trace는 기본적으로 끄고 진단에 필요한 경우에만 활성화한다. 관련 테스트·화면 크기만 선택하고 사용이 끝난 page·context·자신이 시작한 브라우저와 서버를 정리한다. 기존 필수 브라우저·프로젝트 검증을 경량화 때문에 생략하지 않는다.
- 이미지·폰트·CSS·JavaScript를 차단하거나 렌더링 방식을 바꾸는 임의의 Chrome 플래그로 자원을 줄이지 않는다. Chrome을 실행할 수 없으면 이유를 보고하고 다른 엔진 결과를 Chrome 검증으로 표시하지 않는다.
- 대상 페이지와 필요한 상태를 준비하고 폰트·이미지·데이터가 준비됐음을 확인한다. 임의의 sleep보다 해당 화면의 준비 조건과 Playwright의 대기를 사용한다.
- 디자인 검증은 제공된 명세·디자인·이미지와 실제 화면을 비교한다. 스크린샷을 촬영한 뒤 실제로 열어 관련 영역을 확인하고 관찰 결과를 기록한다. 촬영 성공이나 DOM 요소의 존재만으로 디자인 일치를 판단하지 않는다.
- 시각적 회귀 검사는 승인된 비교 기준 이미지가 있을 때 사용한다. 기준 이미지가 없으면 실제 화면을 캡처한 사실과 요구사항 대조 결과를 보고하며, 새 snapshot 저장을 검증 성공으로 간주하지 않는다.
- 자동 이미지 비교는 브라우저 버전·OS·폰트·viewport·배율 등 조건을 맞춘다. 동적 영역을 가리거나 애니메이션을 고정한다면 검증할 결함까지 숨기지 않는지 확인한다.
- 구체적인 설정과 실행 방법은 [Playwright 검증 설정](references/playwright.md)을 읽는다.

## 임시 파일과 증거 정리

- 이번 실행에서 만드는 스크린샷·임시 스크립트·설정은 고유 작업 경로에 두고 생성한 파일을 식별한다. 기존 결과 디렉터리를 일괄 삭제하지 않는다.
- 검증용 임시 스크린샷은 실제로 확인하고 필요한 관찰·판단 근거를 결과에 기록한 뒤 검증 종료 시 삭제한다. 중간 캡처나 같은 내용의 중복 파일을 불필요하게 남기지 않는다.
- 실패 분석·후속 확인 또는 프로젝트의 CI 아티팩트 정책상 필요한 이미지는 보존하고 경로와 이유를 보고한다. 실패 화면을 모두 삭제해 재개에 필요한 근거를 잃지 않는다.
- PR·이슈 첨부까지 요청되었다면 민감정보를 확인해 업로드하고 성공한 첨부 URL을 확인한 뒤 로컬 임시 파일을 삭제한다. 업로드 실패 시 필요한 원본은 유지한다. 검증 요청만으로 업로드하지 않는다.
- 사용자가 제공한 이미지, 승인된 비교 기준 이미지, 기존 테스트·설계 자료는 삭제하지 않는다. 임시 파일 정리는 이번 검증에서 생성한 파일에만 적용한다.

## 결과 전달

- 검증한 코드 상태·환경, 완료 기준과 출처, 실행한 명령·시나리오, 기대 결과와 실제 결과를 연결해 보고한다.
- 각 기준을 통과·실패·미검증으로 구분한다. 기대 동작 자체가 불명확한 항목은 미확정이라고 명시하고 성공·결함으로 임의 판정하지 않는다.
- 직접 실행한 검증과 기존 CI·사용자 제공 결과를 구분한다. 전체 기준을 확인하지 못한 상태에서 검증 완료를 선언하지 않는다.
- 실패·미검증에는 영향과 다음 확인 방법을 기록한다. CI의 통과·차단 및 종료 코드는 프로젝트 정책을 따른다. 정책이 없으면 그 부재를 보고하고 임의의 통과 규칙을 만들지 않는다.
- 보존한 증거는 경로나 업로드 URL을 제공하고, 삭제한 임시 파일을 사용 가능한 첨부처럼 링크하지 않는다.

## 유용한 명령어

변수는 확인한 실제 값으로 채우고 저장소에 설치된 도구를 사용한다. 아래 명령은 필요한 검증만 선택하는 예시다.

```bash
# 대상 코드와 검증 설정 확인
git rev-parse HEAD
git status --short
git diff "$BASE_REF...$HEAD_REF"
rg --files -g AGENTS.md -g package.json -g '*lock*' -g '*playwright*' -g '*test*' -g '*spec*'

# GitHub 자료를 제공받은 경우
gh issue view "$ISSUE_URL" --comments
gh pr view "$PR_URL" --json url,body,baseRefName,headRefOid
gh pr checks "$PR_URL"

# pnpm을 사용하는 저장소의 예시: 설치된 러너와 명명된 Chrome 프로젝트 사용
pnpm exec playwright --version
pnpm exec playwright test --help
pnpm exec playwright test "$TEST_FILE" --project="$CHROME_PROJECT" --workers=1
pnpm exec vitest run "$TEST_FILE"

# Nix 설정 검증 예시
nixfmt --check "$NIX_FILE"
```

Chrome 프로젝트의 실제 `channel`과 headless 설정을 확인한다. `--headed`·`--ui`·`PWDEBUG`로 기본 실행을 바꾸지 않는다. 새 패키지 다운로드, 브라우저 설치, 실제 시스템 설정 활성화를 단순 검사 명령처럼 수행하지 않는다.
