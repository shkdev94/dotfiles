# 좋은 코드 작성

## 목표와 역할

요구한 동작을 정확히 수행하고, 다음 사람이 이해·검증·변경하기 쉬운 코드를 작성한다. 구체적인 구현 선택을 현재 요구사항과 제약에 비추어 판단하는 것이 이 스킬의 역할이다.

코드는 작성 이후 반복해서 읽히고 변경된다. 판단의 중심은 코드의 짧음이나 패턴 이름이 아니라, 다음 사람이 알아야 할 내용과 실수할 가능성을 줄이는 데 둔다.

- 입력은 요구사항, 관련 이슈나 설계 결정, 기존 코드와 호출자, 실행 환경과 저장소 지침이다. 특정 언어·프레임워크·아키텍처를 전제로 하지 않는다.
- 필요한 계약과 변경 경계를 확인하고 이름·데이터 구조·책임·의존성·실패 처리를 정리해 구현한다. 관련 검증과 최종 diff 검토로 결과를 확인한다.
- 결과물은 요청 범위의 코드 변경, 실제 검증 결과, 판단에 영향을 주는 설계 선택과 남은 제약이다.
- 추상적인 깔끔함이나 패턴 적용 개수를 목표로 하지 않는다. 요청과 무관한 재설계, 도구 교체, 의존성 갱신, 커밋·PR 생성·배포로 작업을 확대하지 않는다.
- 이슈 구현이나 테스트 작성 스킬과 함께 사용할 수 있다. 이 스킬은 구현 품질의 판단 기준을 제공하며 다른 스킬의 작업 범위와 결과물 정의를 대체하지 않는다.

## 먼저 동작과 맥락 이해하기

- 저장소의 적용 지침과 주변 코드, 호출자, 기존 테스트를 읽는다. 언어별 관용구와 프로젝트의 구조를 이해한 뒤 변경한다.
- 입력·출력, 허용되는 상태, 중요한 불변 조건, 실패 시 동작을 파악한다. 확정된 요구사항과 구현상의 가정을 구분한다.
- 경계값·빈 값·중복 요청·부분 실패 등 결과를 바꾸는 조건을 해당 작업에 맞게 검토한다. 존재하지 않는 요구사항을 가정해 방어 코드를 늘리지 않는다.
- 기존 계약과 요청이 충돌하면 영향과 근거를 설명한다. 제품 정책이나 호환성을 바꾸는 핵심 결정만 확인하고, 일상적인 구현 선택은 맥락에 맞게 진행한다.

## 읽는 사람이 의도를 알 수 있게 쓰기

- 이름은 도메인의 의미와 역할을 드러낸다. 단위, 시간 기준, 값의 범위가 혼동될 수 있으면 이름이나 타입으로 표현한다. 설명되지 않은 축약어와 의미 없는 범용 이름을 피한다.
- 제어 흐름과 데이터 변환을 따라가기 쉽게 작성한다. 중첩이나 조건이 이해를 방해할 때 가드 절·작은 함수·명시적인 중간값으로 정리한다. 짧게 쓰는 것 자체를 목표로 하지 않는다.
- 함수와 모듈은 서로 관련된 책임을 모은다. 함수 줄 수나 인자 개수로 기계적으로 분리하지 않고, 이름 붙일 수 있는 독립적인 의미와 변경 이유가 있을 때 나눈다.
- 주석은 코드가 그렇게 동작해야 하는 이유, 외부 제약, 주의할 불변 조건을 설명한다. 코드의 동작을 그대로 번역하는 주석보다 코드 자체를 명확하게 만든다.
- 해결한 문제와 관련된 낡은 주석·죽은 분기·임시 디버깅 코드를 정리한다. 주변 전체의 스타일 정리로 확장하지 않는다.

## 책임과 추상화 판단하기

- 함께 바뀌는 정책은 모으고 서로 독립적인 변경 이유는 분리한다. 한 변경 때문에 관계없는 모듈까지 수정해야 한다면 경계를 살펴본다.
- 여러 파일을 함께 수정한다는 사실만으로 합치지 않는다. 같은 정책이 흩어진 것인지, 하나의 기능이 적절한 계층을 거치는 것인지 구분한다.
- 호출자가 알아야 할 개념·설정·호출 순서를 줄이는 인터페이스를 설계한다. 단순한 인터페이스 뒤에 필요한 복잡성을 숨기는 깊은 모듈을 지향하되, 이를 관계없는 책임을 모으는 근거로 쓰지 않는다.
- 자료구조·알고리즘·저장 형식 등 외부에서 알 필요 없는 결정을 모듈 안에 숨긴다. 내부 결정을 바꿀 때 호출자까지 함께 바뀌어야 한다면 공개 계약에 구현 세부사항이 새어 나왔는지 확인한다.
- 인터페이스를 이해하는 비용이 내부 구현을 직접 이해하는 비용과 비슷하다면 그 추상화가 제공하는 이익을 확인한다. 함수 분리나 전달 계층을 늘리는 것만으로 설계가 좋아졌다고 판단하지 않는다.
- 현재 필요한 가장 단순한 설계를 선택한다. 가상의 미래 기능을 위해 플러그인 구조, 상속 계층, 범용 옵션을 미리 만들지 않는다.
- 추상화가 조건·설정·간접 호출을 늘려 이해를 어렵게 하면 도입하지 않는다. 인터페이스나 의존성 주입은 실제 경계, 교체 가능성, 검증 필요성이 있을 때 사용한다.
- 상속·합성·함수·객체·선언형 구성을 일률적으로 우열 판단하지 않는다. 사용 언어와 문제의 성격에 맞는 표현을 선택한다.

## 도메인 경계와 의도적인 중복

- 공통화의 단위는 코드 모양이 아니라 지식과 정책이다. 먼저 “한쪽 정책이 바뀌면 다른 쪽도 반드시 함께 바뀌어야 하는가?”를 묻는다.
- 같은 정책을 여러 곳에서 관리하는 본질적 중복은 하나의 책임으로 모은다. 이해관계자·목적·변경 이유가 다른 정책은 지금 계산식이 같아도 별도로 유지할 수 있다.
- 예를 들어 회원 할인과 첫 구매 쿠폰의 할인율이 모두 10%여도 두 정책이 함께 바뀔 이유는 없다. 각 도메인이 정책을 소유하고, 공유할 필요가 있는 기술적 계산만 별도로 판단한다.
- 공통 함수에 도메인별 플래그와 예외가 계속 늘면 잘못 묶인 정책인지 확인한다. 요청된 변경에 필요하면 호출처별 책임으로 다시 분리하는 방안도 검토한다.
- 날짜 포맷·통화 반올림·문자열 처리도 이름만으로 도메인 중립적이라고 판단하지 않는다. 지역·회계·제품 정책과 입력·출력 계약이 실제로 같은지 확인한다.
- 반복 횟수는 추상화를 검토할 신호일 뿐이다. 세 번 반복되었다고 자동으로 합치거나, 세 번 전까지 동일 정책의 중복을 방치하지 않는다. 확신이 없으면 성급한 결합을 피하고 현재 필요한 범위에서 판단한다.
- 분리 이유가 코드만으로 드러나지 않고 나중에 잘못 합칠 가능성이 높으면 짧은 주석으로 독립적인 변경 이유를 남긴다. 각 정책은 자기 계약을 검증하는 적절한 테스트로 보호한다.

## 테스트 용이성을 설계 피드백으로 사용하기

- 긴 준비 과정, 많은 모킹, 불분명한 기대 결과, 시간·난수·전역 상태 의존은 숨은 입력이나 책임·의존성 경계를 살펴볼 신호다. 테스트가 어렵다는 사실만으로 설계 결함을 단정하지 않는다.
- 테스트를 코드의 첫 번째 호출자로 생각한다. 공개 API만으로 입력을 준비하고 결과를 관찰할 수 있는지 확인한다. 테스트에서 드러난 사용상의 불편을 실제 호출자도 겪는지 살펴본다.
- 개선을 판단할 때 “구조가 단순해져서 테스트가 쉬워졌는가, 내부 접근 통로만 늘어서 쉬워졌는가?”를 구분한다. 의존성 축소·명확한 책임·순수 계산 분리를 우선 검토한다.
- 비공개 함수를 테스트하려고 공개하거나, 모킹만을 위해 인터페이스와 전달 계층을 추가하지 않는다. 의존성 주입은 실제 경계를 명확하게 할 때 사용한다.
- 동작을 보존한 리팩터링마다 테스트가 깨지면 내부 구조·호출 순서에 결합된 검증인지 확인한다. 공개 계약이 바뀐 경우와 구분한다.
- 테스트를 먼저 작성하면 입력·출력 계약을 구체화하는 데 도움이 될 수 있다. 이를 모든 작업의 필수 절차로 만들거나, 테스트 편의를 이유로 요청 범위 밖의 재설계를 수행하지 않는다.

## 원칙이 충돌할 때의 판단

- 원칙과 패턴은 판단 도구다. “DRY나 SOLID를 따라야 해서” 대신, 현재 복잡성·변경 비용·오류 가능성을 어떻게 줄이는지 설명할 수 있어야 한다.
- 국지적으로 더 좋아 보이는 스타일보다 기존 코드베이스의 일관성을 우선한다. 기존 방식에 실제 문제가 있으면 근거를 제시하고 필요한 범위에서 개선한다.
- 내부 이름처럼 되돌리기 쉬운 결정은 빠르게 진행한다. 공개 API·저장 스키마·외부 의존 계약처럼 되돌리기 어려운 결정에는 호환성과 마이그레이션 검토를 더 배분한다.
- 정확성과 요구사항을 충족하는 대안 사이에서는 호출자가 알아야 할 내용, 변경의 파급 범위, 검증 용이성, 되돌리기 비용을 비교한다. 원칙 하나를 극대화하려고 전체 구조를 복잡하게 만들지 않는다.

## 데이터와 상태를 명확하게 관리하기

- 외부 입력과 신뢰 가능한 내부 데이터를 구분한다. 외부 경계에서는 형식뿐 아니라 필요한 도메인 제약을 확인한다. 같은 검증을 모든 내부 계층에서 반복하지 않는다.
- 가능한 경우 타입·자료구조·생성 경계를 이용해 잘못된 상태가 만들어지기 어렵게 한다. 정적 타입만으로 런타임 데이터의 유효성을 보장했다고 가정하지 않는다.
- 상태의 소유자와 변경 경로를 분명히 한다. 같은 사실을 여러 곳에 저장하거나 동기화해야 하는 구조는 필요성을 확인한다.
- 가변 상태와 부수효과는 필요한 범위로 좁힌다. 순수 계산과 입출력을 분리하면 이해와 검증에 도움이 되는 경우 그렇게 구성하되 무조건 계층을 추가하지 않는다.
- 동시성·비동기가 관련되면 작업 수명, 취소, 순서, 자원 해제, 공유 상태 접근을 확인한다. 여러 단계가 하나의 계약이면 중간 실패 후 일관성을 어떻게 유지할지 명확히 한다.

## 실패와 외부 경계 다루기

- 실패를 빈 값·성공 결과로 숨기지 않는다. 복구 가능한 실패는 정의된 정책으로 처리하고, 복구할 수 없으면 호출자가 판단할 수 있는 오류를 전달한다.
- 예외·결과 타입·오류 코드 등 기존 환경의 방식을 따른다. 광범위한 catch나 조용한 fallback을 추가하기 전에 어떤 실패를 처리하는지 명시한다.
- 재시도는 일시적 실패, 중복 실행의 안전성, 횟수와 시간 제한이 정해진 경우에만 사용한다. 무한 재시도나 임의의 대기로 근본 문제를 가리지 않는다.
- 외부 서비스·저장소·파일·프로세스 등 실제로 사용하는 경계의 권한, 타임아웃, 자원 정리와 부분 실패를 검토한다. 입력을 코드나 쿼리에 안전하지 않게 결합하지 않는다.
- 로그에는 원인을 진단할 맥락을 남기되 비밀정보와 민감한 원문을 노출하지 않는다. 처리 단계마다 같은 오류를 중복 기록하지 않는다.

## 변경 규모와 비용 판단하기

- 표면적인 줄 수보다 문제의 원인을 해결하는 최소한의 응집된 변경을 선택한다. 임시 우회나 중복 정책으로 diff만 작게 만들지 않는다.
- 공개 API, 데이터 형식, 저장 상태, 호출자에 영향을 주는 변경은 호환성을 검토한다. 필요한 마이그레이션을 숨기거나 요청 없는 호환성 파괴를 수행하지 않는다.
- 성능은 예상 입력 규모와 실제 제약을 기준으로 판단한다. 명백한 반복 I/O나 불필요한 전체 탐색은 살펴보되, 복잡한 최적화는 측정 또는 구체적인 근거가 있을 때 적용한다.
- 새 의존성은 기존 기능으로 해결 가능한지, 유지 비용과 실행 환경 제약이 어떤지 확인한다. 짧은 코드가 된다는 이유만으로 추가하지 않는다.
- 포맷·이름 취향과 동작 변경을 섞지 않는다. 관련 없는 변경은 별도 작업으로 남긴다.

## 검증과 완료

- 동작과 계약을 기준으로 검증한다. 중요한 규칙·경계·실패 경로에 적절한 테스트를 선택하고, 구현 내부를 그대로 복제한 검증은 피한다.
- 기존 테스트와 저장소의 관련 빌드·정적 검사를 실행한다. 새 테스트는 위험과 기존 검증의 공백을 기준으로 추가한다. 모든 함수에 테스트를 요구하지 않는다.
- 최종 diff에서 요구사항 누락, 잘못된 가정, 호환성 변화, 불필요한 추상화와 중복 상태를 확인한다. 수정으로 생긴 문제를 해결한다.
- 작은 변경은 결과와 검증을 간결하게 보고한다. 중요한 설계 선택이 있으면 선택 이유와 실제 trade-off를 설명하고, 실행하지 못한 검증과 남은 제약을 밝힌다.

## 유용한 명령어

변수는 확인한 실제 값으로 채운다. 필요한 명령만 선택하고, 설치 버전과 저장소의 실행 규칙을 따른다.

```bash
# 관련 코드·도구 설정 찾기
rg --files -g AGENTS.md -g package.json -g pyproject.toml -g Cargo.toml -g go.mod -g flake.nix
rg -n -F -- "$SYMBOL" "$SOURCE_DIR"
# 변경 맥락이 필요한 경우 해당 파일 이력 확인
git log -5 --oneline -- "$FILE_PATH"
git diff --check
git diff -- "$FILE_PATH"
```

빌드·정적 검사·포맷은 저장소에 설정된 명령으로 변경 범위에 맞게 실행한다. 예를 들어 Nix 저장소에서 포맷 수정은 `nixfmt "$NIX_FILE"`로 할 수 있지만 이는 파일을 변경하는 명령이다. 자동 수정이나 전체 저장소 포맷을 단순 검사처럼 실행하지 않는다.
