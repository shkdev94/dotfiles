# 이슈 구현

## 목표와 역할

검토된 GitHub 이슈를 실제 코드 변경으로 구현하고, 완료 기준에 대한 검증 결과와 함께 리뷰 가능한 PR로 전달한다. 확정된 요구사항을 구현으로 연결하는 것이 이 스킬의 역할이다.

- 입력은 대상 이슈의 본문·관련 댓글·검토 자료와 이번 작업의 추가 지침이다. 부분 구현이면 지정된 범위만 맡는다.
- 관련 코드와 기존 동작을 확인하고, 필요한 변경·검증·최종 diff 검토·PR 생성 또는 갱신을 수행한다. 작업 크기와 의존성에 맞게 리뷰 단위를 구성한다.
- 결과물은 구현된 변경, 실제 검증 결과, PR URL과 남은 작업이다. 구현 완료와 전체 이슈 완료를 구분한다.
- 이미 합의한 목적과 범위를 임의로 확대하지 않는다. 별도 요청 없이 이슈를 생성·재할당하거나 PR을 병합·배포하지 않는다.
- 설명, 커밋 메시지, PR 제목과 본문은 한국어로 작성한다.

## 작업 시작과 범위

- 먼저 저장소 루트 `AGENTS.md`와 수정 대상 경로의 추가 지침을 읽는다. 이 스킬은 저장소의 Git 상태 보호, 실행 계획 승인, 새 테스트 추가 제한을 변경하지 않는다.
- 이슈 본문, 관련 댓글과 PR, 이번 할당의 추가 지침을 읽고 목적, 완료 기준, 이번에 맡은 범위와 제외 범위를 확인한다. 부분 작업을 전체 이슈 구현으로 확대하지 않는다.
- 이슈에 정리된 배경 및 검토 결과, 작업 범위, 완료 기준, 검증 방법, 제외 범위와 관련 자료를 구현의 입력으로 사용한다. 특정 섹션 이름이나 모든 항목의 존재를 필수로 요구하지 않는다.
- 사전 검토에서 확정한 결정과 작업 단위를 이어받는다. 구현에 필요한 코드 확인은 수행하되, 이미 합의한 목적이나 설계를 근거 없이 다시 정하거나 검토 절차를 처음부터 반복하지 않는다. 실제 코드와 검토 결과가 충돌하면 근거와 영향을 설명하고, 핵심 범위나 결정의 변경이 필요한 부분만 확인받는다.
- 구현과 PR 생성을 요청한 이슈 할당은 해당 범위의 변경과 PR 전달에 대한 요청으로 취급한다. 실행 환경에서 허용하는 브랜치와 게시 수단을 사용하고, 저장소에서 별도로 요구하는 계획·커밋 승인 절차가 있으면 따른다.
- 승인이 필요한 경우 계획과 필요한 결정을 전달하고 해당 작업을 보류한다. 승인 후에는 기존 계획과 PR 상태를 이어받는다.
- 하위 이슈 생성과 재할당은 별도 요청 없이 수행하지 않는다.
- 시작 브랜치는 할당에서 지정한 값을 사용한다. 지정이 없으면 저장소 기본 브랜치를 조회하며 `main`으로 가정하지 않는다. 선행 PR이 있으면 실제 head 브랜치와 반영 상태를 확인한다.
- 기존 관련 PR과 작업 브랜치를 확인하여 중복 PR을 만들지 않는다. 사용자의 기존 변경과 관계없는 Git 상태를 보존한다.
- 수정 전에 관련 코드, 호출자, 데이터 흐름과 기존 패턴을 확인한다. 공통 원인을 찾아 필요한 최소 범위에서 수정하고, 무관한 정리·포맷팅·리팩터링을 섞지 않는다.

## 리뷰 단위와 stacked PR

- PR 하나는 하나의 설명 가능한 목적과 검증 가능한 변경을 담는다. 작은 작업이나 변경이 강하게 연결되어 분리 이점이 없는 작업은 단일 PR로 완료한다.
- 큰 작업은 목적, 범위, 의존 순서가 명확한 작은 리뷰 단위로 나눈다. 줄 수나 파일 수만으로 기계적으로 분할하지 않는다.
- 각 PR은 자신의 base 위에서 빌드·검증 가능해야 한다. 필요한 문서와 허용된 테스트 변경은 해당 PR에 포함하고 마지막 PR에 몰아넣지 않는다. 새 테스트 추가 여부는 저장소 규칙을 따른다.
- 의존하는 변경은 `시작 브랜치 ← PR 1 브랜치 ← PR 2 브랜치` 순서로 쌓는다. 각 PR의 base는 바로 앞 단계의 브랜치로 설정한다. 독립적인 변경은 억지로 스택에 넣지 않는다.
- 각 PR의 diff에 해당 단계의 추가 변경만 나타나는지 확인한다. 선행 변경을 수정하면 영향을 받는 단계의 정합성과 검증 결과를 다시 확인한다.
- 선행 PR이 병합되면 후속 PR의 base와 diff를 확인한다. rebase나 강제 push가 필요하면 저장소 규칙과 허용된 권한을 따르고, 수행할 수 없는 갱신은 영향을 받는 PR과 함께 보고한다.
- 실행 환경에서 전체 스택을 생성할 수 없으면 지정된 단계만 구현하고 다음 단계의 base와 남은 범위를 전달한다. 단계가 지정되지 않았다면 분할안을 제시하고 작업 단위를 확인한다.

## 구현과 검증

- 이슈의 완료 기준과 기존 코드의 계약·동작을 기준으로 구현한다. 기술 스택별 구현 규칙은 저장소의 지침과 관련 스킬을 적용한다.
- 검증 방법과 명령은 저장소의 지침, 관련 스킬, 실행 스크립트와 CI 설정에서 확인한다. 저장소에서 요구하는 검증을 수행하고, 변경 범위에 맞는 기존 테스트와 빌드·정적 검사 등을 실행한다. 특정 언어나 패키지 매니저를 가정하지 않는다.
- 이슈에 제시된 검증 방법과 기대 결과를 확인하고, 이번 변경 후 완료 기준이 충족되는지 검증한다. 이슈에 기록된 사전 검증은 출처가 있는 참고 결과로 구분하며, 직접 실행한 검증으로 보고하거나 변경 후 검증을 대신하지 않는다.
- 검증이 실패하면 원인을 확인하고 이번 변경으로 발생한 문제를 수정한 뒤 다시 검증한다. 환경 문제나 기존 실패는 근거와 함께 구분한다.
- 최종 diff를 직접 검토하여 요구사항 누락, 회귀, 불필요한 변경, 단계 간 의존성 문제를 확인한다.
- 실행하지 못한 검증은 명령, 이유와 함께 기록한다. 대기 중인 CI나 실행하지 않은 검증을 성공으로 표시하지 않는다.

## 작성 형식

### 브랜치 이름

- 이번 작업에 지정된 브랜치가 있으면 그 이름을 그대로 사용한다. 아래 형식을 맞추려고 브랜치를 바꾸거나 쓰기 가능한 범위 밖에 새 브랜치를 만들지 않는다.
- 브랜치 이름을 직접 지정할 수 있고 생성이 허용된 환경에서는 기존 저장소의 `<분류>/<영문-요약>` 형식을 따른다. 기능은 `feature/`, 버그 수정은 `fix/`를 사용한다. 커밋·PR 제목의 `feat`는 브랜치에서 `feature`로 표기한다. 그 외 분류는 최근 유사 작업의 실제 브랜치 명명 방식을 확인해 따른다.
- 요약은 변경 목적을 나타내는 짧은 영문 소문자와 숫자를 하이픈으로 연결한다. 공백, 한글, `#`은 사용하지 않는다. 이슈 번호나 단계 순서 번호를 필수로 붙이지 않는다.
- stacked PR도 각 단계의 목적에 맞는 동일한 브랜치 형식을 사용한다. 예를 들어 `feature/redact-enhancement`를 base로 `feature/rbac-organization`을 연결한 기존 PR처럼 구성하며, 의존 순서와 이슈 연결은 PR 본문에 기록한다.
- 시작 브랜치나 기존 선행 PR의 브랜치는 이 규칙에 맞춰 변경하지 않는다. 스택 의존 관계는 이름이 아닌 실제 PR의 base와 head로 확인한다.

```text
feature/extract-table-right-panel
feature/organization-admin-page-separation
fix/dataset-document-delete
fix/redact-delete-focus
```

### 커밋과 PR 제목

커밋 메시지와 PR 제목은 다음 형식의 한 줄로 작성한다.

```text
[type] - 한국어 변경 요약
```

- `feat`: 새로운 기능 추가
- `fix`: 버그 수정
- `hotfix`: 긴급 버그 수정
- `refactor`: 동작 변경 없이 구조 개선
- `chore`: 설정, 의존성, 유지보수
- `docs`: 문서 수정
- `style`: 동작 변경 없는 코드 스타일·포맷팅
- `release`: 배포 준비

하나의 커밋에는 하나의 논리적 변경을 담는다. 커밋 메시지는 해당 커밋의 실제 변경을, PR 제목은 해당 PR 전체의 목적을 요약한다. `코드 수정`, `작업`, `변경사항 반영`처럼 모호한 표현을 피한다. 스택에서도 각 PR의 구체적인 목적이 제목에 드러나게 한다.

```text
[feat] - 조직 멤버 초대 기능 추가
[fix] - 검수 완료 후 수정 값 표시 오류 수정
[chore] - 이슈 구현 스킬 추가
```

### PR 본문

아래 형식을 사용하고 안내 문구를 실제 변경 내용으로 대체한다. 후속 작업이 없으면 해당 섹션을 생략한다.

```markdown
## 변경 내용

- 주요 변경과 달라지는 동작을 설명한다.
- 파일 목록보다 무엇을 어떻게 바꿨는지 작성한다.

## 배경

변경이 필요한 이유와 해결하려는 문제를 설명한다.

Closes #이슈번호

## 검증

- 실행한 테스트·빌드·린트 명령과 결과를 기록한다.
- 실행하지 못한 검증은 완료한 검증과 구분한다.

## 후속 작업

- 남은 작업이나 검증, 필요한 이유를 기록한다.
```

- `#이슈번호`를 실제 이슈 번호로 바꾼다. 전체 요구사항을 완료하는 단일 PR 또는 마지막 PR에만 `Closes #번호`를 사용한다. 중간 단계나 부분 구현은 `Refs #번호`로 연결한다.
- 스택의 배경 섹션에는 이번 단계의 범위, 선행·후속 PR 링크와 리뷰 순서를 적는다. 아직 생성되지 않은 PR은 링크를 만들어 쓰지 말고 예정된 작업으로 설명한다.
- 후속 작업에는 남은 구현·통합 검증과 필요한 이유를 기록한다. 현재 PR의 필수 완료 조건이 남았다면 완료로 보고하지 않는다.
- GitHub의 이슈 자동 종료 조건을 확인한다. 기본 브랜치 이외를 대상으로 하는 PR에서 `Closes`만으로 이슈가 자동 종료된다고 가정하지 않는다.
- 구현 도중 범위가 바뀌면 제목과 본문을 최종 변경 기준으로 갱신한다. 폐기한 접근이나 대화 이력은 판단에 필요한 경우에만 포함한다.

## 결과 전달

- 검증 후 PR을 생성하거나 기존 작업 PR을 갱신하고, URL, base, head, 제목, 본문과 diff를 확인한다.
- 브랜치 push나 PR 작성 링크만으로 PR 생성이 완료됐다고 보고하지 않는다. 여러 커밋을 여러 PR로 보고하지 않는다.
- 결과에 PR URL, 이번에 완료한 범위, 실제 실행한 검증과 결과, 남은 작업을 보고한다. 여러 PR이면 각 목적과 의존 순서도 포함한다.
- PR 생성 실패나 권한·환경 제한이 있으면 현재 완료 상태와 필요한 다음 조치를 명확히 설명한다. 확인하지 않은 PR 생성이나 전체 이슈 완료를 주장하지 않는다.
- PR 작성과 검증까지 수행하고 리뷰와 병합은 사용자에게 맡긴다.
