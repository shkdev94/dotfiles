# GitHub 이슈 관리

## 목표와 역할

사용자 요청이나 다른 작업 흐름에서 필요한 GitHub 이슈 작업을 수행한다. 이슈 작성 흐름에는 플랫폼의 형식과 등록 방법을, 구현·PR 작성 흐름에는 원본 요구사항과 이슈 연결·종료 규칙을 제공한다.

- 요청된 조회·검색·생성·수정·댓글·상태 변경만 수행한다. 이슈를 읽거나 연결 규칙을 확인하는 요청을 등록·수정 요청으로 확대하지 않는다.
- 이미 정리된 문제·목적·범위·완료 기준을 사용한다. 등록을 위해 재현, 근본 원인 조사나 구현 설계를 새로 수행하지 않는다.
- 이슈 생성·수정 요청이 명확하면 필요한 플랫폼 작업까지 진행한다. 초안만 요청했거나 계획 모드이면 업로드와 쓰기를 수행하지 않는다.
- 기존 검토 결과와 사용자 내용을 보존하고, 자료에 없는 사실·결정·검증 결과를 추가하지 않는다. 코드 수정, 커밋, PR 게시·병합은 이 스킬의 역할이 아니다.

## 대상과 조회

- 제공된 URL, 대화와 프로젝트 설정에서 GitHub 호스트·저장소·이슈를 확인한다. GitHub 이슈 작업임이 정해진 상태에서 저장소가 생략됐으면 현재 Git 원격도 참고할 수 있다. 번호만으로 다른 저장소의 이슈를 선택하지 않는다.
- `gh` 또는 사용 가능한 GitHub 도구로 조회한다. CLI를 쓰면 설치·인증 상태와 대상 호스트를 확인한다. Enterprise에서는 해당 호스트를 지정한다.
- 요청에 필요한 본문·댓글·상태·메타데이터와 연결된 자료를 읽는다. 구현에 필요한 이슈를 다른 저장소에 복제하지 않는다.
- 중복 검색과 관련 PR 검색 결과는 후보로 취급하고 실제 본문과 범위를 확인한다. 검색 개수 제한이나 불완전한 조회를 전체 결과로 간주하지 않는다.
- 생성·수정 전에는 저장소의 적용 지침, `.github/ISSUE_TEMPLATE`의 관련 양식과 필수 메타데이터를 확인한다. 누락된 필수 값만 확인하며, 이미 알 수 있는 대상과 내용을 다시 요구하지 않는다.

## 이슈 유형과 메타데이터

사용자 지정과 저장소 규칙을 우선한다. 별도 분류가 없으면 정리된 작업 내용을 다음 기준으로 해석한다.

- `Bug`: 예상 밖 동작, 회귀, 실패 또는 기존 동작 규약 위반의 수정. 제공된 현재·기대 동작과 재현·검증 결과를 사용하고 미확정 원인을 단정하지 않는다.
- `Feature`: 새로운 사용자 대상 기능이나 기존 제품 동작의 실질적인 확장.
- `Task`: 유지보수, 리팩터링, 문서화, 테스트, 보안 강화, 운영, 정리, 마이그레이션 등.

이 분류는 라벨 이름이 아니다. 대상 저장소가 제공하는 실제 Issue Type에 맞춰 지정하고, 지원하지 않으면 타입 없이 생성한다. 사용자 지정 분류와 내용이 충돌하면 임의로 의미를 바꾸지 말고 필요한 부분을 확인한다. 저장소의 별도 유형 체계를 위 기본 분류로 덮어쓰지 않는다.

라벨·담당자·마일스톤·프로젝트는 사용자 요청이나 저장소 규칙에 따라 지정한다. `bug`, `enhancement`, `documentation` 라벨로 자동 매핑하지 않는다. 필수 메타데이터를 지정할 수 없으면 초안과 부족한 정보를 남기고 해당 쓰기를 보류한다.

## 등록과 변경

1. 작업 목적과 완료 기준을 보존하면서 저장소 양식에 맞는 제목·본문과 메타데이터를 준비한다. 정리된 초안을 받았다면 새 요구사항을 설계하지 않는다.
2. 신규 등록 전에는 같은 문제 또는 동일한 목적·범위의 열린 이슈를 검색한다. 열린 중복이 있으면 기존 내용을 보존하고 새 내용만 댓글 하나로 보완한다. 추가할 내용이 없으면 기존 이슈를 반환한다. 닫힌 이슈는 관련 이력으로 연결하며, 현재 필요한 작업은 새 이슈로 기록한다. 명시적인 재개 요청이나 저장소 규칙이 있으면 그에 따른다.
3. 기존 이슈 수정에서는 요청된 필드와 내용만 변경한다. 전체 본문을 교체하는 도구라면 최신 본문을 읽고 다른 사용자의 내용을 보존한다. 재할당·종료·재개는 해당 요청이나 적용되는 워크플로 규칙이 있을 때만 수행한다.
4. 필요한 첨부를 반영한 뒤 생성·수정·댓글·상태 변경 중 해당 작업을 실행한다. 여러 줄 본문은 구조화된 도구 인자나 임시 파일과 `--body-file`로 전달하고 셸 코드로 평가하지 않는다.
5. 쓰기 후 다시 조회해 대상·제목·본문·변경한 메타데이터·상태·URL을 확인한다. 응답이 불확실하거나 일부 단계가 실패하면 실제 반영 여부부터 확인하고 중복 생성·댓글을 피한다.

여러 항목은 순차 처리한다. 일부 실패가 독립적인 나머지 항목의 처리를 막지 않도록 하고, 작업별 생성·수정·댓글 보완·기존 이슈 반환·초안·보류·실패 결과와 URL을 보고한다.

## 첨부

- 제공된 스크린샷에서 민감정보를 확인하고, 관련 설명 가까이에 무엇을 보여주는지 짧게 적는다. 스크린샷은 텍스트 설명을 대체하지 않으며 등록을 위해 새로 재현하지 않는다.
- 기존 첨부 URL은 재사용한다. 로컬 파일은 지원되는 업로드 도구로 올린 뒤 반환된 첨부 링크를 본문에 넣는다. 로컬 경로를 웹 링크로 쓰지 않는다.
- 초안만 요청한 경우 업로드하지 않고 첨부 예정 파일을 표시한다. 업로드 실패를 성공으로 보고하지 않으며, 텍스트로 작업을 설명할 수 있으면 등록을 계속한다.
- CLI 업로드와 버전별 옵션, 일부 첨부 실패 후 확인 방법은 [명령별 사용 조건](references/commands.md)을 따른다.

## PR 연결과 상태

GitHub 이슈를 PR에 연결하거나 병합에 따른 종료 여부를 판단할 때는 [PR 연결과 이슈 종료 규칙](references/pull-request-links.md)을 읽는다. 구현에서 확인한 요구사항 충족 범위와 실제 PR base를 기준으로 연결 문구와 후속 조치를 정한다.

PR 본문에 반영하는 작업은 PR 작성 흐름에서 수행한다. 이슈 조회나 연결 문구 작성만으로 이슈를 직접 종료하지 않는다. 상태 변경을 요청받았다면 실제 상태를 다시 확인하고 필요한 변경만 수행한다.

## 도구 사용

GitHub CLI를 사용할 때 필요한 조회·등록·수정·상태 변경·첨부 명령은 [명령별 사용 조건](references/commands.md)을 참고한다. 설치 버전이 지원하는 옵션과 필드만 사용하며, 사용 가능한 다른 GitHub 도구에도 같은 대상 확인과 결과 검증 기준을 적용한다.
