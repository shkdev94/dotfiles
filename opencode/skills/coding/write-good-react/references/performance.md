# 요청·번들·렌더링 성능

성능 문제나 데이터 흐름을 수정할 때 사용한다. 측정한 병목과 해당 프로젝트의 버전·캐시·배포 환경에 적용되는 항목만 선택한다.

## 요청의 의존성과 실패

- 입력과 권한이 확보된 독립 요청은 함께 시작하고 필요한 곳에서 결과를 기다린다. 앞 요청의 결과가 필요한 작업이나 순서가 계약인 쓰기는 순서를 보존한다.
- `Promise.all`은 모든 결과가 필요한 경우에 사용한다. 하나가 실패하면 전체 대기가 실패하지만 다른 요청이 자동 취소되는 것은 아니므로, 부분 실패 허용 여부와 취소·정리 방법을 별도로 판단한다.
- 쓰기를 병렬화해 중복 실행이나 순서 변경을 만들지 않는다. 목록별 요청 폭증이 있으면 batching, 페이지네이션과 동시 실행 수 제한을 검토한다.
- 클라이언트 데이터는 기존 프레임워크·쿼리 계층의 중복 요청 제거와 캐시를 활용한다. 이미 쓰는 도구로 해결할 수 있는데 새 라이브러리를 추가하지 않는다. 캐시 키에는 결과를 구분하는 사용자·필터·페이지 조건을 반영한다.
- 수동 비동기 요청은 이전 요청이 새 화면 상태를 덮어쓰지 않도록 취소하거나 응답의 유효성을 확인한다. 네트워크 실패를 빈 목록으로 숨기지 않는다.

## Next.js 서버·클라이언트 경계

- Next.js의 버전과 라우터를 확인하고 데이터 조회·캐시 기본값을 해당 버전의 문서로 확인한다. Server Component와 클라이언트 요청의 캐시 수명을 동일하게 취급하지 않는다.
- 상호작용이 필요한 경계만 Client Component로 만들고, 서버 전용 의존성과 비밀 값이 클라이언트 번들로 전달되지 않게 한다.
- 클라이언트에는 실제 화면이 사용하는 직렬화 가능한 값만 전달한다. 도메인 객체 전체나 필요 없는 중첩 데이터를 넘기지 않는다.
- 독립 영역의 로딩이 전체 화면을 막으면 지원되는 데이터 흐름과 Suspense·스트리밍 경계를 사용한다. 일반적인 Effect 기반 요청을 Suspense로 감싸는 것만으로 스트리밍이 생긴다고 가정하지 않는다.
- 요청 단위 중복 제거와 요청 간 캐시는 구분한다. 공유 캐시는 사용자 간 데이터 격리, 무효화·만료·용량과 배포 인스턴스의 수명을 정한 경우에 적용한다. 모듈 전역 Map을 모든 배포에서 유효한 공유 캐시로 가정하지 않는다.
- Server Action이나 서버 함수는 호출자가 직접 접근할 수 있는 경계로 취급한다. 각 작업에서 필요한 인증·인가와 입력 검증을 수행한다. 화면에서 버튼을 숨기는 것으로 권한을 보장하지 않는다.

## 번들과 렌더링

- 초기 화면에 필요 없는 큰 기능은 지원되는 동적 import로 나누고 로딩·오류 상태를 제공한다. 첫 화면에 필요한 콘텐츠까지 지연시키거나 SSR을 일괄 비활성화하지 않는다.
- 큰 패키지의 import 비용이 문제이면 번들 결과와 공식 공개 entry point를 확인한다. 지원되는 하위 경로 import나 프레임워크 최적화를 사용하고 비공개 `dist/` 경로에 의존하지 않는다. barrel import를 전부 금지하지 않는다.
- 컴포넌트를 다시 그리는 실제 원인과 비용을 확인한다. 불필요한 Effect·상위 상태 갱신·넓은 구독을 먼저 줄이고, 비싼 계산이나 안정된 props 경계에만 메모이제이션을 적용한다.
- Effect 의존성을 줄이려고 필요한 값을 누락하지 않는다. 객체나 함수가 필요 없이 매번 바뀌는 문제는 생성 위치와 책임을 조정한다.
- transition은 늦게 반영해도 되는 UI 갱신에 사용한다. 입력 자체의 즉시 갱신이나 필수 쓰기의 성공 처리를 미루는 용도로 사용하지 않는다.
- SSR 초기 렌더링에서 브라우저 전용 값·현재 시각·난수로 출력이 달라지지 않게 한다. `suppressHydrationWarning`이나 임의의 주입 스크립트를 기본 해결책으로 삼지 않는다.
- 긴 웹 목록은 실제 DOM·레이아웃 비용과 접근성·검색 요구를 보고 가상화를 검토한다. 단순 계산에 복잡한 캐시를 추가하는 최적화는 측정 근거가 있을 때 선택한다.
