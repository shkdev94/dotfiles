# 일반 유닛 테스트

## 무엇을 검증할지

- 비즈니스 계산, 파싱·변환, 입력 검증, 상태 전이의 공개 계약을 검증한다.
- 의미 있는 동치 클래스를 선정하고 경계 바로 안·밖, 빈 값, 잘못된 입력, 실패 결과를 계약에 맞게 다룬다. 모든 입력 조합을 기계적으로 나열하지 않는다.
- 정상 경로만 검증하지 말고 실제로 위험한 실패 경로를 포함한다. 라이브러리가 이미 보장하는 동작을 중복 검증하지 않는다.
- 변경 후 결과 외에 계약상 필요한 불변성, 입력 미변경, 실패 시 상태 보존도 검증한다.
- 같은 규칙을 여러 입력으로 확인할 때만 매개변수화한다. 서로 다른 시나리오를 조건문 많은 테스트 하나에 넣지 않는다.

## 구조와 경계

- Arrange에서 입력과 필요한 경계 대역을 준비하고, Act에서 대상의 공개 API를 호출하고, Assert에서 구체적인 출력·오류·외부 효과를 확인한다.
- 비공개 함수를 내보내거나 내부 필드에 접근하는 방식으로 테스트 구조를 맞추지 않는다. 테스트 편의를 위한 제품 구조 변경은 별도 필요성을 판단한다.
- 파일 시스템·시계·외부 서비스 등 통제해야 하는 경계만 대체한다. 순수 함수나 가까운 협력 객체는 실제 구현을 사용하는 것을 우선한다.
- 비동기 결과와 예외는 반드시 await하거나 러너가 기다릴 수 있게 반환한다. 검증 없이 예외를 삼키는 catch는 사용하지 않는다.
- 실패 시 이유를 알 수 있도록 구체적인 값과 오류 유형을 검증한다. 단순 truthy 검증으로 중요한 계약을 대신하지 않는다.

예를 들어 할인 계산은 실제 할인 정책에 근거한 입력과 예상 금액을 직접 사용한다. 기대값을 대상 함수와 같은 수식으로 다시 계산하지 않는다. 정책에 없는 반올림이나 허용 범위를 테스트에서 임의로 결정하지 않는다.

## 우선순위와 생략 판단

- 가격·할인·수수료·환불·세금 등 금액 정책은 높은 우선순위로 검증한다. 적용 순서, 소수점 정밀도, 반올림 시점, 최소·최대 금액처럼 실제 계약에서 중요한 부분을 선정한다.
- 외부 데이터 파싱·변환은 누락 필드, 잘못된 형식, 허용된 변형, 실제 실패 사례를 검증한다. 실제 입력은 민감정보를 제거하고 핵심 조건만 남긴 픽스처로 보존한다.
- 상태 전이는 허용되는 전이와 금지되는 전이, 실패 시 기존 상태 보존을 검증한다. 날짜·정규식은 경계와 예상 밖 입력 중 계약에 해당하는 사례를 선정한다.
- 분기 수가 많거나 설명에 예외 조건이 반복되면 우선 검토할 신호로 삼는다. `if` 개수만으로 대상이나 테스트 개수를 결정하지 않는다. 실패 영향과 기존 검증 범위를 함께 판단한다.
- 개발 중 수동 계산이나 콘솔 출력으로 확인했던 사례는 중요한 계약을 보장하는지 판단해 자동 테스트로 옮긴다. 일회성 디버깅 출력을 모두 테스트로 만들지는 않는다.
- 단순 위임도 인자 변환, 권한, 오류 변환 등 자체 계약이 있으면 검증한다. 단순 상수의 값 복사나 외부 라이브러리 자체의 정확성 검증은 피하고, 우리 코드의 정책 적용과 연동을 검증한다.

## 경계값과 규칙 조합

- 의미 있는 임계값은 바로 아래·일치·바로 위를 검토하고 해당 입력 영역에 맞는 값을 선택한다. 금액의 최소 단위나 시간 정밀도를 가정하지 않는다.
- 같은 규칙의 사례는 러너가 지원하는 `test.each` 또는 동등한 표 기반 기능으로 정리한다. 케이스 이름에 입력과 기대 결과가 드러나도록 한다.
- 개별 규칙만으로 놓치는 조합도 검증한다. 예를 들어 무료배송과 지역 추가 요금이 함께 적용되는 경우의 기대값은 실제 정책에서 가져온다.
- 모든 분기의 모든 조합을 요구하지 않는다. 누락을 찾을 때 분기 커버리지를 참고할 수 있지만, 높은 수치를 동작 검증의 증거로 취급하지 않는다. 결과 검증 없이 실행만 하는 테스트를 추가하지 않는다.

## 픽스처와 기대값

- 공유되는 거대한 가변 객체 대신 필요한 필드만 가진 테스트별 데이터를 사용한다. 반복 생성은 `makeOrder({ total: 50000 })` 같은 팩토리로 정리하고, 호출마다 중첩 데이터까지 독립적인 객체를 반환한다.
- 테스트에 중요한 값은 본문에서 보이게 하고, 팩토리의 기본값이 핵심 조건을 숨기지 않게 한다.
- 기대값은 수동 계산이나 독립적인 명세·검증 자료로 정한다. 구현을 복제한 수식과 자동 생성 결과를 검토 없이 정답으로 쓰지 않는다.
- 변환 결과의 구조 자체가 계약이고 크기가 검토 가능할 때 인라인 스냅샷을 사용할 수 있다. 먼저 결과의 정확성을 확인하고, 변동 필드는 필요한 경계에서 고정한다. 큰 출력은 핵심 필드를 명시적으로 검증한다.
- 스냅샷이 바뀌면 정책 변경인지 회귀인지 판단한다. 통과시키기 위한 일괄 갱신은 하지 않는다.

## 테스트하기 어려운 코드

- 긴 준비 과정이나 모킹 설정은 책임 과다·숨은 의존성·부적절한 경계를 살펴볼 신호다. 설정 길이만으로 설계 결함이라고 단정하지 않는다.
- 기존 공개 API와 의존성 주입 지점을 먼저 활용한다. 내부 헬퍼를 테스트 목적으로만 export하지 않는다.
- 헬퍼가 독립적인 도메인 책임을 갖는다면 모듈 분리를 제안할 수 있다. 제품 구조 변경은 요청 범위와 필요성을 확인한 뒤 수행한다. 테스트 작성 요청을 자동으로 리팩터링 작업으로 확대하지 않는다.
- 시간·난수·환경은 실제 러너가 지원하는 방식으로 고정하고 복원한다. 시스템 시각 설정에 fake timer 활성화가 필요한지 확인하고, 타임존·자정·윤일 등의 사례는 해당 정책과 관련될 때만 추가한다.
