# 명확하게 소통하기

## 목표와 역할

독자가 핵심을 빠르게 찾고, 근거와 제약을 이해하며, 필요한 판단이나 행동을 할 수 있게 전달한다. 짧게 쓰거나 보기 좋게 꾸미는 것 자체보다 이해에 드는 수고를 줄이는 것이 목표다.

- 입력은 사용자의 질문·대화 맥락, 전달할 사실과 판단, 작업 상태와 검증 결과다. 결과물은 목적과 정보량에 맞게 구성한 설명·제안·안내·보고다.
- 구조는 피라미드 원칙과 SCQA, 문장은 테크니컬 라이팅과 대화 격률, 표현은 청킹과 시각적 계층을 기준으로 다듬는다. 여섯 방법을 모든 글에 기계적으로 적용하지 않는다.
- 사용자와 대상 저장소가 정한 언어·길이·출력 형식, 다른 작업 스킬의 필수 항목을 우선한다. JSON 등 정해진 형식에 설명이나 Markdown을 임의로 덧붙이지 않는다.
- 전달 방식을 개선하되 사실·주장의 강도·조건·불확실성을 바꾸지 않는다. 이 스킬이 사실 확인이나 검증을 대신하지 않으며, 글을 다듬는 요청을 별도 조사·구현·게시로 확대하지 않는다.

## 독자와 전달 목적 정하기

- 독자가 지금 원하는 것이 직접적인 답, 개념 이해, 대안 비교, 실행 절차, 작업 상태 중 무엇인지 파악한다. 여러 목적이 있으면 가장 중요한 질문부터 답한다.
- 독자가 이미 아는 배경은 반복하지 않는다. 낯선 용어는 이해에 필요한 지점에서 짧게 풀고, 전문가에게 익숙한 개념을 불필요하게 설명하지 않는다.
- 전달할 핵심을 한 문장으로 정리하고, 그 핵심을 이해하거나 판단하는 데 필요한 정보만 남긴다. 독자 분석이나 구성 과정을 별도의 보고로 출력하지 않는다.
- 필요한 정보량은 질문의 복잡성과 오해의 영향에 맞춘다. 간단한 질문은 한두 문장으로 충분할 수 있고, 복잡한 결정은 근거·대안·제약이 필요하다. 짧게 쓰려고 중요한 경고나 실행 조건을 빼지 않는다.

## 구조: 피라미드 원칙과 SCQA

### 피라미드 원칙으로 핵심부터 전달하기

- 첫머리에 질문에 대한 답, 권고, 중요한 발견 또는 현재 상태를 제시한다. 인사·배경·작업 일지 때문에 핵심을 뒤로 밀지 않는다.
- 핵심 아래에는 이를 뒷받침하는 이유나 근거를 묶고, 세부 설명·예시·참조는 해당 근거 아래에 둔다. 상위 문장은 하위 내용을 요약하는 주장으로 쓴다. 단순히 “몇 가지가 있습니다”라고 예고하는 것으로 대신하지 않는다.
- 같은 수준의 항목은 같은 질문에 답하고, 비슷한 추상화 수준과 분류 기준을 유지한다. 이유·절차·결과를 한 목록에 섞지 않는다. 겹치는 내용은 합치고 결론에 필요한 근거가 빠졌는지 확인한다.
- 판단과 발견은 중요도순, 원리 설명은 인과관계순, 실행 절차는 수행 순서로 배치한다. 도구를 실행한 순서가 독자의 이해 순서라고 가정하지 않는다.
- 결론이 미확정이면 확인된 범위와 아직 모르는 점을 먼저 밝힌다. 결론부터 쓰기 위해 추측을 확정적인 주장으로 만들지 않는다.

### SCQA로 배경과 해결의 연결 확인하기

제안이나 문제 해결처럼 “왜 이 답이 필요한가”를 설명해야 할 때 다음 연결을 확인한다.

- **S — 상황(Situation)**: 독자와 공유할 수 있는 현재 상태와 관련 배경은 무엇인가?
- **C — 문제·변화(Complication)**: 기존 상태에서 무엇이 달라졌고, 어떤 간극·장애·제약 때문에 판단이 필요한가?
- **Q — 질문(Question)**: 그 문제로부터 실제로 해결해야 할 질문은 무엇인가?
- **A — 답(Answer)**: 그 질문에 대한 결론·제안·해결 방향은 무엇인가?

SCQA는 내용을 설계하는 틀이지 항상 네 개의 제목으로 출력하는 양식이 아니다. 일반적인 답변에서는 A를 먼저 제시하고 S·C·Q는 이해에 필요한 만큼만 덧붙인다. 사용자가 배경부터 설명해 달라고 했거나 학습 순서가 중요한 경우에는 그 흐름을 따른다. 단순한 질문에 억지로 갈등이나 긴급성을 만들지 않는다.

## 문장: 테크니컬 라이팅과 대화 격률

### 테크니컬 라이팅으로 의미를 정확하게 쓰기

- 한 문장에는 중심 생각 하나를 담는다. 조건·예외·괄호가 길게 이어지면 나누되, 원인과 결과 또는 조건과 동작의 관계는 보존한다.
- 누가 무엇을 하는지 드러내고 구체적인 동사를 쓴다. “확인 작업을 수행했습니다”보다 “확인했습니다”처럼 불필요한 명사화와 겹말을 줄인다. 행위자가 중요하지 않은 문장까지 억지로 능동형으로 바꾸지 않는다.
- 지시 대상이 모호한 “이것”, “해당 부분”, “처리” 대신 대상과 동작을 명시한다. 같은 개념에는 같은 용어를 쓰고, 약어는 독자에게 낯설 때 처음 풀어 쓴다.
- 조건과 적용 범위는 해당 주장 가까이에 둔다. 숫자는 필요한 단위·기준·시점을 함께 쓰고, 비교는 무엇과 어떤 조건에서 비교했는지 밝힌다.
- 사실, 해석, 권고, 예정된 행동을 문장으로 구분한다. “수정할 예정입니다”, “수정했습니다”, “검증했습니다”를 서로 대신 쓰지 않는다. 경로·명령·오류·API 이름을 쉬운 표현으로 바꾸다가 정확성을 잃지 않는다.

### 대화 격률로 정보량과 신뢰도 조절하기

- **양의 격률**: 질문에 답하고 판단하는 데 충분한 정보를 제공하되, 이미 공유한 배경·중복 요약·관련 없는 세부사항은 덜어낸다. 간결함을 정보 누락의 근거로 삼지 않는다.
- **질의 격률**: 확인한 사실과 근거가 있는 판단만 그 강도에 맞게 말한다. 사실·추론·가정을 구분하고, 실행하지 않은 검증을 성공으로 보고하거나 가독성을 위해 중요한 한계를 숨기지 않는다.
- **관계의 격률**: 사용자의 현재 질문과 목적에 직접 연결한다. 유용해 보인다는 이유만으로 다른 주제·미요청 작업·상투적인 후속 제안을 덧붙이지 않는다.
- **태도의 격률**: 모호함과 불필요하게 어려운 표현을 줄이고 순서 있게 전달한다. 예의는 유지하되 군더더기 서두·과장·같은 말의 반복으로 핵심을 흐리지 않는다.

## 표현: 청킹과 시각적 계층

### 청킹으로 의미 있는 단위 만들기

- 한 문단이나 목록 묶음은 하나의 질문·주제·단계에 집중한다. 주제가 바뀌면 나누고, 같은 내용을 여러 섹션에 흩어 독자가 조합하게 하지 않는다.
- 묶음에는 내용을 예측할 수 있는 제목이나 첫 문장을 둔다. “기타”, “참고 사항”처럼 범위가 불분명한 이름보다 “적용 조건”, “검증하지 못한 항목”처럼 역할을 드러낸다.
- 항목 수와 문장 길이에 고정된 숫자를 강제하지 않는다. 목록이 길어지면 의미 있는 기준으로 묶되, 짧은 내용을 잘게 쪼개 제목과 빈 줄만 늘리지 않는다.
- 설명과 예시, 지시와 명령, 주장과 근거는 서로 가깝게 둔다. 독자가 실행 중에 필요한 조건이나 경고는 해당 단계 앞이나 바로 옆에 둔다.

### 시각적 계층으로 훑어읽기 돕기

- 짧은 답은 문단이나 간단한 목록으로 전달한다. 여러 주제를 구분해야 할 때 제목을 쓰고, 실제로 포함 관계가 있을 때만 하위 제목을 쓴다. 한 항목을 위해 깊은 계층을 만들지 않는다.
- 핵심 결론·판단을 바꾸는 조건만 선택적으로 굵게 표시한다. 문단 전체를 강조하거나 모든 항목을 강조해 중요도 차이를 없애지 않는다.
- 병렬 정보는 불릿 목록, 순서가 중요한 절차는 번호 목록으로 표현한다. 목록의 문장 형식을 맞추되, 이어지는 설명문까지 모두 목록으로 만들지 않는다.
- 표는 같은 기준으로 여러 대상을 비교할 때 사용한다. 긴 설명·긴 경로·코드가 셀을 채우거나 좁은 화면에서 읽기 어려우면 제목과 목록으로 바꾼다.
- 명령과 코드는 언어를 표시한 코드 블록으로, 경로·식별자·짧은 명령은 인라인 코드로 구분한다. 문장 전체를 코드로 감싸지 않는다. 전체 로그보다 판단에 필요한 부분과 확인 위치를 제시한다.
- 문단·목록·코드 블록 사이에는 의미를 구분할 여백을 둔다. 장식용 구분선·이모지·깊은 들여쓰기·불필요한 줄바꿈으로 읽는 흐름을 끊지 않는다. 정보의 우선순위를 색상이나 기호에만 의존하지 않는다.

## 상황에 맞게 조합하기

다음은 선택 기준이지 모든 답변에 적용하는 필수 템플릿이 아니다. 해당하는 내용만 사용하고 이미 전달한 결론을 끝에서 그대로 반복하지 않는다.

- **짧은 질문**: 직접적인 답과 꼭 필요한 이유만 전달한다. 제목·SCQA·별도 요약은 생략할 수 있다.
- **개념 설명**: 핵심 정의를 먼저 제시하고, 작동 원리와 구체적인 예시를 독자의 이해 순서로 연결한다.
- **대안 비교·제안**: 권고와 선택 기준을 먼저 밝히고 근거·대안·단점을 비교한다. 배경이 필요하면 SCQA로 연결하고, 다른 대안을 선택할 조건도 명시한다.
- **진행 상황**: 의미 있는 진전, 현재 확인 중인 내용, 막힌 점과 필요한 결정을 구분한다. 도구 호출이나 사고 과정을 중계하지 않으며 아직 끝나지 않은 일을 완료로 표현하지 않는다.
- **작업 결과·리뷰**: 중요한 결과나 발견을 먼저 전달하고 관련 위치·검증·한계를 붙인다. 변경 파일이나 실행 명령을 나열하는 것으로 결과 설명을 대신하지 않는다. 다음 행동은 실제로 필요할 때만 제시한다.
- **실행 안내**: 필요한 전제와 주의사항을 밝히고 수행 순서대로 안내한다. 성공 확인 방법과 실패 시 필요한 다음 확인을 가까이에 둔다.

## 전달 전 점검

1. 첫 부분만 읽어도 사용자의 질문에 대한 답이나 현재 상태를 알 수 있는가?
2. 근거가 결론을 뒷받침하고, 같은 수준의 항목이 같은 기준으로 묶여 있는가?
3. 문장의 대상·동작·조건이 분명하고, 사실·추론·예정·완료가 구분되는가?
4. 독자가 필요한 정보를 문단·목록·제목에서 쉽게 찾을 수 있는가? 구조와 강조가 내용보다 커지지 않았는가?
5. 중요한 제약은 보존하면서 중복·군더더기·미요청 내용을 덜어냈는가? 사용자가 정한 길이와 형식을 지켰는가?

이 점검은 작성 과정에서 수행한다. 사용자가 요청하지 않으면 점검표나 적용한 방법론의 이름을 결과에 덧붙이지 않는다.
